# 트레이딩·백테스팅 프레임워크 설계 개념 모델

> 전략 실행(트레이딩) 엔진과 백테스팅 시뮬레이터를 같은 코드 경로로 운영하는 시스템에 대하여
> 2개의 기반 원칙과 설계 결정 15축 

---

## 이 문서의 성격

이 문서는 **개념 수준의 참조 모델** 이다.
서술은 일반적인 소프트웨어 아키텍처 및 금융 시스템 설계 원리에 기반한다.

**주요 순서:** 각 결정은 `문제 → 결정 → 불변식 → 트레이드오프 → 실패 징후 → 검증` 순으로 서술한다.
불변식은 "이걸 깨면 시스템이 조용히 틀린 답을 낸다"는 뜻이다.

**이 문서는 이 저장소의 규칙이 아니다.** 일반 원리에 기반한 참조 모델이며, 여기 적힌 결정이
VMTrader에 그대로 구현되어 있다는 뜻이 아니다. 잣대이지 서술이 아니다.

**실제 적용 상태의 정본은 [`architecture-map.md`](architecture-map.md) §6이다.** 축별로
`준수` / `부분` / `미준수(부채)` / `불채택` 중 하나와 그 근거가 거기 있다.

**일부 축은 의도적으로 불채택했다.** 전제가 다르기 때문이며, 대표적으로 D2 불변식 3
("백그라운드 스레드는 전부 데몬으로 만든다")은 상주 데몬을 전제하지만 이 저장소의 라이브
세션은 cron 단발이다([ADR-0009](adr/0009-cron-oneshot-live-session.md) ·
[ADR-0008](adr/0008-task-queue-fill-pump.md)). 이 문서와 코드가 어긋나 보이면 먼저 §6을
확인할 것 — 대개 어긋난 것이 아니라 채택하지 않은 것이다.

## Part 0. 두 개의 기반 원칙

설계 결정이 아니라 **모든 결정을 구속하는 제약**이다. 성능이나 편의를 이유로 완화하지 않는다.

### 원칙 1 — 데이터 정직성: 결측은 허용, 날조는 금지

시장 데이터는 반드시 빈다. 휴장, 상장폐지, 벤더 장애, 비유동 종목의 무거래 구간.
이때 시스템이 취할 수 있는 태도는 둘뿐이다.

| 태도 | 결과 |
|---|---|
| **부재를 위로 전파** | 전략이 정직한 결정을 내린다 — 스킵하거나, 경고하거나, 중단한다 |
| **그럴듯한 값으로 메움** | 전략이 존재하지 않았던 시장에서 거래한 것처럼 보이는 결과를 만든다 |

두 번째는 편리하다. 백테스트가 죽지 않고 끝까지 돌기 때문이다. 그리고 **그래서 위험하다.**

**금지 목록**

- 봉 합성 (없는 시각의 OHLC를 만들어내기)
- 직전값 캐리포워드 (장중 실행 판단용으로)
- 상수 기본값 대체 (지표가 없으면 "평균적인 값"을 넣기)
- 결측 구간 보간

**캐시 부기 행에 대한 특칙**

"이 날짜를 조회했고 데이터가 없었다"를 기록하는 placeholder 행은 캐시 효율상 필요하다.
그러나 이 행은 **전략에 도달하기 전에 반드시 걸러져야 하고**, 부재 사실은 별도 신호로 호출자에게 전달해야 한다.
placeholder를 실제 봉으로 오인해 반환하는 것이 이 원칙을 깨는 가장 흔한 경로다.

**왜 이것이 기술 판단이 아니라 위험 통제인가**

가짜 데이터 위에서 내려진 결정은 가짜 손익을 만든다. 그 손익이 고객이나 투자자에게 제시되면
기술 부채가 아니라 **평판·법적 문제**가 된다. 따라서 이 원칙은 코드 리뷰에서 협상 대상이 아니다.

**집행 방법**

- 합성 데이터를 도입하는 변경은 명시적 승인 없이는 거부한다.
- "합리적 기본값으로 결측을 가려서 통과시키는" 테스트는 테스트가 아니라 **은폐 장치**다.
  결측이 올바르게 전파되는지를 단언하는 테스트로 교체한다.
- 모든 공급자 경로에 동일하게 적용한다. 예외를 하나 만들면 그 경로가 사고 지점이 된다.

### 원칙 2 — 시뮬레이션·실환경 동형성

백테스트의 목적은 "좋아 보이는 곡선"이 아니라 **실제 운용 결과의 예측**이다.
따라서 시뮬레이터는 실제 체결 환경의 동작을 모방해야 하고, 둘의 의미론이 어긋나면 백테스트는 신뢰할 수 없다.

**검증을 3단계로 계층화한다.** 위로 갈수록 증거력이 강하다.

| 단계 | 방법 | 증거력 |
|---|---|---|
| **회귀 검증** | 저장된 기준 실행 결과와 대조해 드리프트 탐지 | 변화를 알려줄 뿐, 옳음을 증명하지 않는다 |
| **경계 감사** | 알려진 난구간(세션 경계, 휴일, 조기 폐장, 계약 롤, 반올림)을 수동 검토 | 보조 증거 |
| **실거래 재현** | **실제로 체결된 구간을 재생해, 실제 체결가와 실현 손익을 허용오차 내로 재현** | **유일한 결정적 증거** |

많은 팀이 첫 단계를 "정확도 검증"이라 부르며 멈춘다. 그러나 회귀 검증은 **어제의 자신과 비교하는 것**이라
어제도 틀렸다면 오늘도 조용히 틀린 채로 통과한다. 3단계 없이는 정확도를 주장하지 않는 편이 정직하다.

**우선순위 규칙:** 정확성이 먼저, 속도는 그 다음. 단 속도 개선은 **의미론을 바꾸지 않는 범위**에서만 허용한다.
"빠르지만 조금 다르게 동작하는" 최적화는 반려한다.

## Part I. 실행 모델 (D1~D5)

### D1. 경로 의존 루프 — 스텝 순서 자체가 정확성 요건

**문제**
백테스트 한 스텝에서 "전략 실행", "주문 처리", "시계 전진"을 어떤 순서로 할 것인가.
그리고 이 루프를 병렬화할 수 있는가.

**결정**
순서를 고정하고, 단일 시뮬레이션에 대해 **직렬 실행을 강제**한다.

```
① 전략 로직 실행 (사용자 코드)
② 대기 주문 평가 및 체결 처리
③ 시뮬레이션 시계 전진
```

**불변식**

1. 이 순서는 관례가 아니라 **요건**이다. 현금 잔고, 포지션 수량, 조건부 주문 그룹의 상태,
   파생상품 생명주기, 평가손익이 모두 직전 스텝의 결과에 의존한다(경로 의존).
2. 하나의 시뮬레이션 실행에는 **하나의 전략만** 참여한다.
   다중 전략을 한 실행에 섞으려는 시도는 조용히 인터리브하지 말고 **거부**한다.
3. 스레드를 늘리면 동작이 보존될 것이라 가정하지 않는다. 사용자 전략은 자유형 코드이며
   가변 상태를 갖는다. 자동 병렬화의 대상이 아니다.

**병렬화가 유효한 지점 — 이 셋뿐이다**

| 영역 | 방식 |
|---|---|
| 데이터 수화(hydration) | 청크 병렬 다운로드, 선행 프리페치, 다중 자산 팬아웃 |
| 서로 독립인 실행 | 파라미터 스윕, 기간 스윕, 전략 비교 → **프로세스/컨테이너 단위**로 분리 |
| 실행 내부의 제한적 배칭 | 동일 시각 다중 자산 가격 일괄 조회 |

**트레이드오프**
단일 실행의 처리량 상한이 코어 하나로 묶인다. "10개를 동시에" 필요하면
스레드가 아니라 **프로세스 수준 동시성**으로 푼다.

**실패 징후**
동일 입력에 대해 실행마다 결과가 미세하게 다르다. 스텝 순서를 바꾼 뒤 손익이 바뀐다.

**검증**
동일 시드·동일 입력 반복 실행의 **비트 단위 동일성**. 순서 변경 시 회귀 대조.

### D2. 동시성 경계 — 단일 소비자 메시지 파이프라인

**문제**
실거래에서는 WebSocket 콜백, 폴링 루프, 타이머 등 여러 스레드가 동시에 상태 변경 사건을 만든다.
이들이 공유 상태(포지션, 현금, 주문 추적)를 직접 만지면 락 지옥이 된다.

**결정**
락으로 공유 상태를 보호하는 대신, **상태를 한 스레드가 독점**하고 나머지는 메시지를 보낸다.
액터 모델의 메일박스 구조다.

```
[WS 스레드]    ─┐
[폴링 루프]    ─┼─→ [큐] ─→ [소비자 스레드 1개] ─→ 핸들러 실행
[타이머 스레드] ─┘                  ↑
                        여기서만 상태를 만진다 = 락 불필요
```

**단일 소비자가 무료로 제공하는 3가지 보장**

| 보장 | 의미 |
|---|---|
| 상호배제 | 두 사건이 절대 동시에 처리되지 않는다 |
| 순서 | FIFO. 체결 다음 취소가 뒤집히지 않는다 |
| 원자성 | 핸들러가 끝날 때까지 중간 상태가 외부에 노출되지 않는다 |

락 서너 개로 만들어야 할 보장을 **"소비자를 하나로 둔다"** 는 규칙 하나로 얻는다.

**2단 분리를 권장한다**

책임이 다른 두 소비자를 나누면 지연 특성을 분리할 수 있다.

| 단계 | 상태 | 요구사항 |
|---|---|---|
| 1단: 브로커/시장 상태 | 포지션, 현금, 주문 추적 | **빠르고 정확해야** — 느리면 사건이 유실된다 |
| 2단: 전략 상태 | 사용자 변수, 사용자 콜백 | **느려도 된다** — 무엇을 할지 알 수 없다 |

사용자 콜백이 외부 API를 5초 호출해도 1단의 사건 수신은 멈추지 않는다.

**불변식**

1. 소비자 스레드에서 메시지를 보내고 **그 결과를 기다리지 않는다.** 자기 자신을 기다리는 교착이 된다.
2. 1단 상태를 만지는 코드에 락을 추가하지 않는다. 락이 필요해졌다면 **단일 소비자 전제가 이미 깨진 것**이므로
   락을 더할 게 아니라 왜 깨졌는지를 찾는다.
3. 백그라운드 스레드는 전부 데몬으로 만든다. 하나라도 비데몬이면 프로세스가 종료되지 않는다.

**트레이드오프**

- 소비자 스레드가 죽으면 시스템 전체가 멎는다. 핸들러 예외를 반드시 삼켜서 루프를 지킨다.
  성숙한 액터 프레임워크는 supervisor 재시작을 제공하지만, 직접 구현할 때는 "절대 죽지 않기"에 의존하게 된다.
- 스택 트레이스가 "누가 이 사건을 보냈는지"에서 끊긴다. 메시지에 **상관관계 ID**를 실어 완화한다.
- 백프레셔 정책을 반드시 정해야 한다 (D2-a).

**D2-a. 백프레셔 — 큐가 가득 차면?**

| 정책 | 대가 | 적합한 곳 |
|---|---|---|
| 폐기 | **데이터 유실**. 상위는 유실 사실조차 모를 수 있다 | 정합 루프가 복구해주는 경우에 한해 |
| 블로킹 | 생산자(WS 수신)가 멈춰 벤더 연결이 끊길 수 있다 | 생산자가 재시도 가능할 때 |
| 무제한 큐 | 소비가 밀리면 메모리 폭주 | 소비 속도가 확실히 우세한 경우 |

**어느 정책을 택하든 유실·지연을 계측해 노출한다.** 조용히 버리는 큐는 사고의 온상이다.
폴링 기반 공급자는 다음 정합 사이클이 유실을 복구하지만, 순수 push 기반에는 그런 안전망이 없다.

**실패 징후**
간헐적으로 체결이 반영되지 않는다. 종료 시 프로세스가 남는다. 부하 시 상태 불일치가 늘어난다.

**검증**
큐 유실 카운터를 지표로 노출. 부하 테스트에서 사건 수 대비 처리 수 일치 확인.

### D3. 실행 모드 전환 — 비동기 버퍼 ↔ 동기 패스스루

**문제**
D2의 큐는 실거래에 필수지만 시뮬레이션에는 독이다.
시계를 전진시키기 전에 상태가 확정되어야 하는데(D1 ③), 큐는 처리 시점을 비결정적으로 만든다.

**결정**
같은 파이프라인이 **실행 정책(dispatcher)** 만 바꿔 두 모드로 동작하게 한다.

| 모드 | 정책 | 스레드 경계 | 순서 |
|---|---|---|---|
| 실거래 | 큐에 적재, 별도 스레드가 처리 | 2개 | FIFO |
| 시뮬레이션 | **호출 스레드에서 즉시 처리** | 0개 | 호출 순서 = 실행 순서 |

**불변식**

1. 두 모드가 **동일한 핸들러 코드**를 탄다. 시뮬레이션 전용 사건 경로를 별도로 만들지 않는다.
   경로가 갈리는 순간 원칙 2(동형성)가 무너진다.
2. 모드 선택은 **한 곳에서** 결정한다. 호출부마다 플래그를 붙이는 방식은
   새 사건을 추가하는 사람이 플래그를 빠뜨려 결정론을 깨뜨린다.

**설계 조언**
호출부 플래그(`dispatch(..., sync=True)`)보다 **주입된 정책 객체**가 낫다.
전자는 정책이 수십 곳에 흩어지고, 후자는 한 줄로 모인다.

**실패 징후**
시뮬레이션 결과가 실행마다 미세하게 다르다. 특정 사건만 다음 스텝에서 반영된다.

**검증**
동일 입력 반복 실행의 완전 일치. 새 사건 타입 추가 시 결정론 회귀 테스트.

### D4. 주문 상태 기계와 부모-자식 관계

**문제**
주문은 생성 → 제출 → (부분)체결 / 취소 / 거부 / 만료의 상태를 갖고,
조건부 주문 그룹(진입+손절+익절, 택일 그룹, 선행-후행)은 부모-자식 관계를 형성한다.
이 전이를 명시하지 않으면 각 브로커 어댑터가 제각기 해석한다.

**결정**
상태를 열거형으로 명시하고, 전이를 문서화된 상태 기계로 관리한다.

**불변식**

1. **상태 필터는 열거형만 받는다.** 원시 문자열 필터를 허용하면 오타가 조용한 버그가 된다
   (`"partial_fill"` vs `"partal_fill"`은 예외 없이 빈 결과를 낸다).
2. **부모 주문은 원칙적으로 현금을 움직이지 않는다.** 실제 체결되는 자식이 움직인다.
   예외는 부모 자체가 진입 다리인 그룹 유형뿐이며, 이를 명시적으로 열거한다.
3. **자산군별 현금 처리 규칙을 명시한다.** 증거금 기반 상품(선물), 현물 결제 상품,
   계약형 상품은 체결 시 현금 반영 방식이 서로 다르다. 기본값을 하나로 두면 반드시 어긋난다.
4. 상태 **변경 요청**(제출/취소/수정) 실패는 **시끄럽게 실패**한다. D13의 관대한 읽기 정책을 여기에 적용하지 않는다.
5. 부분 체결은 누적 수량과 가중평균 체결가를 함께 갱신한다. 마지막 체결가로 덮어쓰지 않는다.

**흔한 설계 부채 — 사건 이름과 상태값의 겸직**

사건 토픽 상수(`"체결됨"`)와 주문 상태값(`"체결됨"`)을 **같은 문자열로 두면**
한 상수가 두 개념을 겸직하게 되고, `order.status = EVENT_FILLED` 같은 대입이 자연스럽게 퍼진다.
초기에는 편하지만 이후 어느 쪽도 독립적으로 바꿀 수 없게 된다.
**처음부터 분리할 것.** 사건은 타입, 상태는 열거형으로.

**실패 징후**
그룹 주문에서 현금이 두 번 차감된다. 취소된 부모의 자식이 계속 살아 있다.
브로커마다 같은 상황의 상태 문자열이 다르다.

**검증**
상태 전이 표를 테스트로 인코딩. 그룹 유형별 현금 영향 단위 테스트.

### D5. 체결 가능성 판정 — 캘린더가 아니라 데이터

**문제**
"시장이 닫혀 있을 때 주문은 어떻게 되는가?"
거래소 캘린더로 판정하면 24시간 시장, 혼합 자산 전략, 조기 폐장, 벤더별 데이터 범위 차이에서 전부 어긋난다.

**결정**
전략이 선언한 시장/스케줄은 **깨어나는 시점을 정하는 편의 장치**로만 쓰고,
**체결 가능 여부는 해당 자산의 실제 데이터 존재 여부로 판정**한다.

**불변식**

| 규칙 | 내용 |
|---|---|
| R1 | **장중 합성 봉을 만들지 않는다.** 지표를 왜곡하고, 폐장 시각 체결을 허용하며, 진짜 데이터 문제를 은폐한다 |
| R2 | 체결에는 실행 가능한 가격원이 필요하다. **체결 데이터 우선 → 없으면 호가 → 둘 다 없으면 체결 불가** |
| R3 | 세션 공백은 "데이터 없음"이다. 체결 없음, 대기 주문은 **유효 상태로 대기**하다가 데이터 재개 시 평가된다 |

**왜 데이터 기준이 캘린더 기준보다 나은가**

- 혼합 자산 전략(암호화폐 + 선물 등)이 하나의 스케줄 아래서 각자 올바르게 동작한다
- 조기 폐장, 임시 휴장, 유지보수 시간을 캘린더에 하드코딩하지 않아도 자연히 반영된다
- 벤더가 정규장만 제공하는 경우와 연장시간까지 제공하는 경우를 구분해 처리할 필요가 없다

**주의 — 커버리지 판정 함정**
정규장 범위만 제공하는 피드에 대해 "하루 끝(23:59)까지 데이터가 있어야 완결"이라고 판정하면
캐시가 **영원히 미완결**로 남아 무한 재조회 루프에 빠진다.
완결 기준은 **"요구 시각 이전의 마지막 세션 종료"** 로 정의한다.

**실패 징후**
폐장 시간대에 체결이 발생한다. 워밍된 캐시인데도 반복해서 재조회한다.

**검증**
휴일·조기 폐장·유지보수 공백 구간에 대한 체결 부재 단언.

## Part II. 가격과 평가 (D6~D7)

### D6. 체결가와 호가의 분리 — 가장 저평가되는 결정

**문제**
"현재가"를 묻는 하나의 함수를 두면, 구현자는 결국 편의를 위해 폴백을 넣는다.
체결가가 없으면 호가 중간값을, 그것도 없으면 직전 값을. 그 순간 두 개념이 섞인다.

**결정**
**두 개의 별도 접근자**를 두고, 절대 서로 폴백하지 않는다.

```
체결 기반 조회   →  실제 거래된 가격만 반환. 호가로 폴백하지 않는다. 절대로.
호가 기반 조회   →  매수/매도 호가와 그로부터 유도된 중간값(mark)
```

**불변식**

1. 체결 기반 조회는 **오래된 값을 반환할 수 있고, 그것이 정상**이다.
   비유동 상품(특히 옵션)은 몇 시간 동안 거래가 없을 수 있다. 실제 거래 환경도 오래된 체결가를 준다.
2. 호가는 **거래가 없어도 존재한다.** 이것이 두 개념을 분리해야 하는 근본 이유다.
3. 평가손익과 비유동 시장 체결 모델링에는 **호가 유도 중간값**을 쓴다. 체결가가 아니다.

**왜 중요한가**
이 경계가 무너지면 시뮬레이션이 실제보다 낙관적이 된다.
실제 환경에서는 체결가가 오래되어 판단을 미루게 되는 상황에서,
시뮬레이터만 호가로 매끄럽게 폴백해 "항상 가격이 있는" 세계를 만들기 때문이다.

**실패 징후**
비유동 상품 백테스트가 실거래보다 일관되게 좋다. 실거래에서 "가격이 없다"는 상황이 백테스트에 없다.

### D7. 평가 폴백 사다리와 "나쁜 0" 문제

**문제**
평가손익 계산 시 가격을 얻지 못하면 무엇을 반환할 것인가.
`0`을 반환하면 포지션 가치가 사라지고, 다음 날 가격이 잡히면 되돌아온다.
결과는 톱니 모양 자산 곡선이며, 실제로는 아무 일도 없었는데 큰 손실과 회복이 반복된 것처럼 보인다.

**결정**
명시적 폴백 사다리를 정의하고, **`0`을 실패 표현으로 쓰지 않는다.**

```
① 호가가 실행 가능하면 → 중간값(mark)
② 아니면 → 최근 체결가
③ 그것도 없으면 → "평가 불가" 신호(null)를 반환
   → 상위가 직전 유효 평가액을 유지(forward-fill)
```

**불변식**

1. **`0`은 유효한 값이다.** 실패 표시로 쓰면 유효한 0과 구분할 수 없다.
   실패는 `null` 같은 별도 표현으로 알린다. 이 규칙은 잔고·포트폴리오 가치 조회에도 동일하게 적용한다.
2. 호가의 0값(한쪽 호가 부재)은 **실행 불가로 간주**해 걸러낸다. 그대로 중간값 계산에 넣으면 절반 가격이 나온다.
3. 평가용 forward-fill은 **원칙 1의 예외가 아니다.** 이것은 시장 데이터를 지어내는 것이 아니라
   *"새 정보가 없으니 마지막으로 알려진 평가액을 유지한다"* 는 회계 처리다.
   단, **체결 판단에는 절대 쓰지 않는다.** 평가와 실행의 경계를 지킨다.

**주의**
평가 forward-fill이 길어지면 자산 곡선이 계단 모양이 된다. 이는 버그가 아니라
"이 기간 동안 이 포지션을 평가할 수 없었다"는 **사실의 정직한 표현**이다.
숨기지 말고 경고로 노출해 사용자가 데이터 커버리지 문제를 인지하게 한다.

**실패 징후**
자산 곡선의 인접일 수익률이 큰 폭으로 부호를 번갈아 가며 튄다.
잔고 조회 실패가 0으로 기록되어 포트폴리오가 사라진 것처럼 보인다.

**검증**
일별 수익률 분포에서 극단값(±20% 이상)의 인접일 부호 반전 빈도를 측정.

## Part III. 데이터 공급 (D8~D10)

### D8. 공급자 추상화와 표현 계층 분리

**문제**
공급자마다 데이터 형식, 조정 상태(분할/배당 반영 여부), 시간 정렬, 커버리지 범위가 다르다.
이를 전략에 노출하면 전략이 공급자에 종속된다.

**결정**
추상 기반 클래스로 인터페이스를 고정하고, 공급자별 차이는 어댑터 안에서 흡수한다.

```
DataSource (추상)
 └ BacktestingDataSource (추상)
    ├ 표현 A 기반 계열   ← 공급자 다수
    └ 표현 B 기반 계열   ← 특정 공급자 전용
```

**불변식**

1. 서로 다른 dataframe 엔진(예: 행 지향 vs 열 지향 라이브러리)을 쓰는 계열은
   **인터페이스가 비슷해 보여도 상호 교체 불가**다. 이 사실을 문서와 타입으로 명시한다.
   한쪽 계열의 버그를 고치면서 다른 계열 코드를 함께 수정하는 실수가 반복적으로 발생한다.
2. **시간 정렬을 어댑터에서 정규화한다.** 일봉이 자정으로 타임스탬프되면
   그 날의 고저종가가 장 시작 전에 관측 가능해져 **미래 정보 누출**이 된다.
   세션 종료 시각으로 정렬하고, 이 변환은 **멱등**이어야 하며 캐시 적재/조회/신규 수신 **모든 경로**에 적용한다.
3. 조정 상태(분할 반영 여부)를 어댑터 속성으로 노출한다. 호출자가 추측하게 두지 않는다.

**실패 징후**
공급자를 바꾸면 결과가 크게 달라진다. 일봉 전략이 비현실적으로 좋다(누출 의심).

### D9. 계층 캐시와 버전 무효화

**문제**
시장 데이터 조회는 느리고 비싸며 종종 유료다. 캐시는 필수지만,
잘못된 데이터가 캐시에 들어가면 버그 수정 후에도 계속 잘못된 결과가 나온다.

**결정**
3계층으로 구성하고, 무효화는 **버전 키**로 한다.

```
① 로컬 파일 캐시     빠름, 프로세스/컨테이너 재시작에 취약
② 원격 객체 저장소   팀·환경 간 공유, <접두사>/<버전>/<상대경로>
③ 버전 키           증가시키면 전체가 무효화된다
```

**불변식**

1. **버전 증가는 파괴적 작업이다.** 운영 환경에서는 기본적으로 금지하고
   예외적으로만, 영향 범위를 계산한 뒤 수행한다. 재구축이 비싼 데이터셋(옵션 체인 등)은 특히 그렇다.
2. 문제가 의심되면 **먼저 캐시된 실제 데이터를 내려받아 검증**한다.
   런타임 전용 버그일 수 있고, 그렇다면 캐시를 지워도 낫지 않는다.
3. 삭제가 필요하면 **최소 범위**로 한다. 전체 무효화는 마지막 수단이다.
4. 캐시 루트 경로 설정은 **모듈 적재 이전**에 결정되어야 한다. 이후 변경은 반영되지 않는다.
5. 오염 데이터(전 항목 0인 행 등)는 **적재 시점에 필터링**해 캐시가 자가 치유되게 한다.

**트레이드오프**
버전 키 방식은 단순하지만 입자가 거칠다. 세밀한 무효화가 필요하면
스키마 버전과 데이터 버전을 분리하거나 데이터셋별 버전을 둔다.

### D10. 설정 우선순위 — 환경이 코드를 이길 것인가

**문제**
데이터 공급자 선택 같은 설정을 코드에서 지정하게 할 것인가, 환경변수로 덮어쓸 수 있게 할 것인가.

**결정**
운영 유연성이 필요하면 **환경이 코드를 덮어쓰게** 한다. 단 이 사실을 크게 문서화한다.

```
공급자_선택=<이름>   → 코드에 명시된 클래스를 무시하고 이것을 사용
공급자_선택=none     → 코드가 지정한 것을 사용
공급자_선택={JSON}   → 자산군별 라우팅
```

**불변식**

1. **이것은 놀라운 동작이다.** "코드에 썼는데 왜 안 먹지?"는 신규 기여자가 가장 자주 겪는 혼란이다.
   문서 최상단과 로그 양쪽에서 실제 선택 결과를 알린다.
2. 라우팅에서 정확한 대상이 없을 때 **조용히 유사한 것으로 대체하지 않는다.**
   원칙 1에 따라 결측으로 처리한다. (예: 특정 통화쌍 데이터가 없으면 다른 통화쌍으로 몰래 바꾸지 않는다)
3. 설정 항목을 추가·변경하면 문서를 **같은 변경셋에서** 갱신한다.
   나중에 하기로 한 설정 문서는 갱신되지 않는다.

## Part IV. 회계 (D11~D12)

### D11. 기업행위 멱등성

**문제**
분할·배당 조정 함수가 실행 중 여러 번 호출되면 조정이 중첩 적용되어 가격이 왜곡된다.
호출 횟수는 캐시 적중 패턴에 따라 달라지므로 **비결정적으로 틀린다**.

**결정**
조정 함수는 **멱등**해야 한다. 조정 완료 표시를 데이터에 남기고 재적용을 차단한다.

**불변식**

1. 조정 함수 진입부에서 표시를 확인하고, 있으면 즉시 반환한다. 완료 후 표시를 남긴다.
2. 조정 로직을 고치면 **캐시 버전을 올려** 과거의 잘못 조정된 데이터를 무효화한다(D9와 연동).
3. 배당 적용은 **(날짜, 종목) 단위로 1회**만 기록·적용한다. 하루에 여러 번 호출되는 구조를 전제한다.
4. **가격 조정과 현금 지급을 동시에 하지 않는다.** 배당을 현금 사건으로 처리한다면
   가격 시리즈는 배당 미조정이어야 한다. 둘 다 하면 **수익이 이중 계상**되어 성과가 부풀려진다.
5. 배당액과 가격 시리즈의 **단위를 일치**시킨다. 미조정 배당액을 분할 조정된 가격 시리즈에 그대로 쓰면
   주당 금액이 수십 배 커진다.
6. 파이프라인에서 이미 정규화된 시리즈에 대해 **하위 계층에서 조정을 다시 적용하지 않는다.**

**실패 징후**
성과 지표가 비현실적으로 높다. 실행마다 결과가 미묘하게 다르다.
특정 종목만 특정 기간에 이상하다.

**검증**
조정 함수 2회 연속 호출 후 결과 동일성 단언. 독립 데이터 출처와의 가격 대조.

### D12. 외부 현금흐름의 분리

**문제**
입출금, 이자, 수수료 같은 비거래 현금 이동이 전략 성과에 섞이면
"전략이 잘한 것"과 "돈을 더 넣은 것"을 구분할 수 없다.

**결정**
비거래 현금 이동을 **명시적 사건 타입**으로 모델링하고, 성과 계산에서 분리한다.

**제공할 인터페이스**

- 입금 / 출금 / 임의 조정 (각각 사유 문자열 포함)
- 금융비용 설정: 계좌 유형(신용/현금), 일수 기준, 금리 결측 시 정책
- 금리 갱신

**불변식**

1. `null`은 "변경 없음", `0`은 "명시적으로 0"이다. 두 의미를 구분한다.
2. 계좌 유형이 음수 현금 허용 여부를 결정한다. 현금 계좌에서 음수 잔고가 나오면 오류다.
3. 모든 현금 사건은 **사유와 함께 감사 기록**에 남긴다.

## Part V. 운영 (D13~D15)

### D13. 비대칭 복원력 — 읽기는 관대하게, 쓰기는 엄격하게

**문제**
외부 시스템은 예고 없이 새로운 주문 유형, 상태값, 상품군, 계좌 행을 반환한다.
알 수 없는 행 하나 때문에 전체 동기화를 실패시키면 시스템이 자주 멈춘다.
반대로 주문 제출 실패를 삼키면 사용자가 체결됐다고 착각한다.

**결정**
**방향에 따라 정반대 정책**을 적용한다.

| 방향 | 정책 |
|---|---|
| 외부 상태 **읽기**·파싱 | **관대**. 미지의 값은 `UNKNOWN`으로 보존하고 원본을 첨부한 뒤 경고. 식별자나 수량이 아예 없는 행만 건너뛴다 |
| 상태 **변경 요청**(제출/취소/수정) | **엄격**. 실패는 즉시 시끄럽게 실패 |

**불변식**

1. 부분 파싱으로 결과가 불완전할 때, **부재를 이유로 기존 추적 상태를 삭제하지 않는다.**
   파싱된 항목만 갱신한다.
2. 잔고 조회 실패 시 `0`을 쓰지 않는다(D7 불변식 1과 동일 원리).
   실패를 알리고 마지막 알려진 값을 유지한다.
3. 읽기 관대 정책을 쓰기 경로에 적용하지 않는다. **이 혼동이 가장 위험한 실수**다.

### D14. 스케줄링과 생명주기

**문제**
전략은 언제 깨어나는가. 그리고 그 시점이 시뮬레이션과 실거래에서 어떻게 대응되는가.

**결정**
생명주기 훅 순서를 고정하고, 시간 진행 방식만 모드별로 교체한다.

```
초기화
 └ (일별) 개장 전 → 거래 반복 × N → 폐장 전 → 폐장 후
```

**불변식**

1. **훅 순서는 두 모드에서 동일**하다. 시뮬레이션은 시계를 앞당기고, 실거래는 실제로 기다릴 뿐이다.
2. 대기(sleep) 동작을 모드별로 교체한다. 시뮬레이션에서는 실제 대기 대신
   **큐 배수 + 시계 전진**을 수행한다. 이 지점이 D1 ③과 D2를 잇는 접합부다.
3. 생명주기 훅 진입·이탈 시 사건 큐를 배수한다. 이 지점을 명시하지 않으면
   사용자 콜백이 오래된 상태를 보게 된다.
4. 중단 신호는 **단일 지점**에서 확인한다. 모든 훅 호출이 이 게이트를 통과한다.
5. 24시간 시장은 폐장 로직을 우회한다. 폐장까지 남은 시간을 무한대로 두는 것이 단순하고 안전하다.

### D15. 관측성과 성능 예산

**문제**
장기 실행 시뮬레이션은 수십만 스텝을 돈다. 이 규모에서는
**로그 출력 자체가 지배적 비용**이 되어 계산보다 오래 걸릴 수 있다.

**결정**
스텝 단위 비용을 예산으로 관리하고, 진단용 기능은 기본 비활성화한다.

**불변식**

1. 스텝별 상태 로그, 지역 변수 캡처 같은 진단 기능은 시뮬레이션에서 **명시적 활성화(opt-in)** 로 둔다.
2. 진행 상황은 로그가 아니라 **구조화된 파일/지표**로 노출한다.
   외부 UI가 폴링할 수 있어야 하고, 실행 시작 직후 첫 기록이 생겨야 한다
   (그렇지 않으면 "멈춘 것처럼" 보인다).
3. 진행 기록에는 **경량 직렬화 형태**를 쓴다. 전체 객체 직렬화는 이 빈도에서 비싸다.
4. 실행 산출물에 **버전 정보를 포함**한다. 사후 재현성의 최소 조건이다.
5. 데이터 수화가 오래 걸리는 구간에도 **하트비트**를 남긴다.
   시계가 멈춘 것과 프로세스가 죽은 것을 외부에서 구분할 수 있어야 한다.
6. 후처리(리포트/차트/통계) 실패가 **시뮬레이션 성공을 가리지 않게** 한다.
   실패를 단계별로 분류하고(시뮬레이션 / 후처리 / 업로드), 거래 기록만이라도 살린다.

## Part VIII. 도입 체크리스트

새 시스템을 설계하거나 기존 시스템을 감사할 때 순서대로 확인한다.

**기반**
- [ ] 결측 데이터의 처리 방침이 문서화되어 있고, 모든 공급자 경로에 동일하게 적용되는가
- [ ] 캐시 부기용 행이 상위로 새어나가지 않음을 테스트가 단언하는가
- [ ] 정확도 검증이 회귀 대조에서 멈추지 않고 실거래 재현까지 계획되어 있는가

**실행**
- [ ] 시뮬레이션 스텝 순서가 문서화되어 있고 변경 시 회귀 테스트가 도는가
- [ ] 공유 상태를 만지는 스레드가 정확히 하나인가
- [ ] 백프레셔 정책이 정해져 있고 유실이 계측되는가
- [ ] 백그라운드 스레드가 전부 데몬인가
- [ ] 시뮬레이션 모드가 동기 실행이고, 그 선택이 한 곳에서 이루어지는가
- [ ] 주문 상태 전이표가 테스트로 인코딩되어 있는가
- [ ] 사건 타입과 상태값이 분리되어 있는가

**가격·데이터**
- [ ] 체결가 조회가 호가로 폴백하지 않음을 테스트가 단언하는가
- [ ] 평가 실패가 `0`이 아닌 별도 표현으로 전달되는가
- [ ] 일봉 타임스탬프가 세션 종료에 정렬되어 미래 정보 누출이 없는가
- [ ] 조정 함수가 멱등하고, 2회 호출 결과 동일성이 테스트되는가
- [ ] 캐시 버전 무효화의 운영 절차와 금지 사항이 문서화되어 있는가

**운영**
- [ ] 읽기와 쓰기의 복원력 정책이 명시적으로 구분되어 있는가
- [ ] 진단 기능이 기본 비활성화이고 활성화 방법이 문서화되어 있는가
- [ ] 실행 산출물에 버전 정보가 포함되는가
- [ ] 후처리 실패가 시뮬레이션 결과를 가리지 않는가

## 부록. 배경 개념 요약

이 문서에서 전제한 패턴들의 간단한 정의.

**단일 소비자 이벤트 파이프라인**
Observer 패턴 + 스레드 안전 큐 + 소비자 스레드 1개.
Observer만 쓰면 발행자 스레드에서 콜백이 실행되어 결국 락이 필요해진다.
큐를 끼우고 소비자를 하나로 묶으면 상호배제·순서·원자성을 규칙 하나로 얻는다.

**액터 모델**
상태를 전용 스레드로 감싸고 메일박스로만 접근시키는 동시성 모델(Hewitt, 1973).
액터는 메시지를 받으면 ① 다른 액터에 메시지 전송 ② 새 액터 생성 ③ 다음 처리 행동 변경만 할 수 있고,
**다른 액터의 상태를 직접 읽거나 쓸 수 없다**. 사실상 "스레드까지 확장된 캡슐화"다.
이벤트 버스와의 차이는 주소 지정 방식이다 — 버스는 토픽으로, 액터는 인스턴스로 보낸다.

**경로 의존성**
현재 상태가 과거 상태 전체의 순서에 의존하는 성질.
이 성질을 갖는 계산은 순서를 바꾸거나 병렬화하면 결과가 달라진다.

**멱등성**
같은 연산을 여러 번 적용해도 결과가 한 번 적용한 것과 같은 성질.
재시도·캐시 적중 패턴이 결과를 바꾸지 않게 하는 핵심 도구.

**백프레셔**
생산 속도가 소비 속도를 초과할 때의 처리 정책.
폐기·블로킹·무제한 버퍼 중 하나를 반드시 선택해야 하며, "정하지 않음"은 선택지가 아니다.
