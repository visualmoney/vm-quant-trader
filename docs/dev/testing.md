# 테스트 정책

| 항목 | 내용 |
| --- | --- |
| 문서 성격 | 살아있는 문서 — 코드와 같은 커밋에서 갱신한다. 실측 수치는 담지 않는다 |
| 한 줄 정의 | **무엇이 테스트로 강제되고 있으며, 왜 그것이 강제되는가** |
| 독자 | 엔진 기여자 — 테스트를 고치거나 새로 쓰는 사람 |
| 여기 없는 것 | 커버리지 하한값, CI 매트릭스, 개별 테스트의 근거, 실전 승격 기준, 스모크 절차 — 전부 정본이 따로 있다(§8) |
| 푸시 전 | `./scripts/check.sh` — 스위트·`ruff`·커버리지 하한을 한 번에(§0) |

이 문서는 **정책**을 적는다. 커버리지 비율, 테스트 케이스 수, 실행 시간, 변형 주입 검출률 같은 실측값은 적지 않는다. 숫자를 적는 순간 이 문서는 특정 시점의 스냅샷이 되고, 다음 커밋에서 조용히 틀린 문서가 된다. 측정값의 자리는 [`reports/`](reports/)와 CI다.

---

## 0. 푸시 전에 무엇을 돌리는가

```sh
./scripts/check.sh
```

**`pytest`만으로는 CI를 대신하지 못한다.** CI는 셋을 본다 — 스위트, `ruff`, 그리고
`.coveragerc`가 잡고 있는 커버리지 하한. `pytest tests/`는 그중 하나만 본다.

| 무엇 | 어디서 강제되나 | `pytest tests/`가 보나 |
| --- | --- | --- |
| 스위트 | CI의 Test 단계 | 예 |
| 스타일 | CI의 Lint 단계 (`ruff check`) | **아니오** |
| 커버리지 하한 | `.coveragerc`의 `fail_under` — `--cov` 없이는 재지 않는다 | **아니오** |

스크립트는 그 셋을 한 번에 돌린다. 이것이 별도 문서 항목인 이유는, **초록색 스위트를
근거로 푸시했다가 빨간 CI를 만나는 일이 실제로 있었기 때문**이다 — 그리고 그때 깨져
있던 것은 공백 두 줄이었다.

CI는 여기에 `--locked`를 더해 `uv.lock`이 `pyproject.toml`에서 밀렸는지도 본다. 그것은
작업 트리가 아니라 러너의 재현성에 대한 검사라 스크립트에 넣지 않았다.

## 1. 테스트 계층

| 계층 | 위치 | 무엇이 들어가는가 |
| --- | --- | --- |
| 단위 | `tests/unit/` | 모듈 하나의 계약. 패키지 구조를 그대로 미러링한다 — `vmtrader/broker/live/worker.py`의 테스트는 `tests/unit/broker/live/test_worker.py`다 |
| 단위 (경계) | `tests/unit/` 직하 | 어느 한 모듈에 속하지 않는 전역 불변식. `test_vendor_import_boundary.py`, `test_abstract_base_classes.py`가 그것이다 |
| 단위 (`scripts/`) | `tests/unit/` 직하 | `scripts/`는 패키지가 아니므로 `importlib`로 파일을 직접 적재해 테스트한다. `test_kis_gateway.py`·`test_kis_smoke.py`·`test_promotion_check.py`·`test_fetch_holidays.py`가 이 형태다 |
| 통합 | `tests/integration/` | 모듈 여러 개를 실제로 조립해 돌리는 것. 한 사이클 또는 한 백테스트 전체가 단위다 |

**새 모듈을 추가할 때의 규칙.**

| 새로 추가하는 것 | 테스트를 두는 곳 |
| --- | --- |
| `vmtrader/` 아래 모듈 | 같은 경로를 미러링한 `tests/unit/` 아래. 디렉터리가 없으면 만든다 |
| 조립 경로를 바꾸는 변경(세션·핸들러·사이저의 배선) | `tests/integration/trading/`. 단위 테스트만으로는 배선이 뚫려 있는지 알 수 없다 |
| `scripts/` 아래 실행 스크립트 | `tests/unit/` 직하에 `test_<script>.py`. 스크립트는 실주문·실계좌를 만지므로, "얼마를 어디에" 결정하는 부분은 계좌에서 발견하지 말고 여기서 고정한다 |
| 전역 불변식(import 경계, 인터페이스 목록 등) | `tests/unit/` 직하. 미러링하지 않는다 — 대상이 특정 모듈이 아니기 때문이다 |

픽스처는 세 곳에 나뉜다. 전역 헬퍼는 `tests/conftest.py`, 통합 트레이딩 픽스처 경로는 `tests/integration/trading/conftest.py`, 나머지는 각 테스트 파일 안의 지역 헬퍼다. 지역 헬퍼를 우선한다 — 공용 픽스처는 그것을 쓰는 모든 테스트의 전제를 한 파일에 숨기기 때문이다.

`pyproject.toml`에 pytest 설정 절이 없다. 마커도 `testpaths`도 없으므로 **`pytest`는 언제나 전건을 수집한다.** "느린 테스트는 기본 실행에서 뺀다" 같은 선택적 실행 경로는 존재하지 않으며, 도입하려면 그 자체가 정책 변경이다.

## 2. 네트워크·SDK 무의존

**전 스위트는 브로커 SDK가 설치되지 않고 네트워크가 닿지 않는 환경에서 통과한다.** 이것은 관례가 아니라 요구사항이며([`spec/kis-broker.md`](spec/kis-broker.md) NFR-2·NFR-3), 신뢰가 아니라 단언으로 강제된다.

강제하는 것은 `tests/unit/test_vendor_import_boundary.py`다. 이 테스트는 모듈을 **import하지 않고** `ast`로 소스를 읽어 판정한다. 위반이 파일과 줄 번호로 보고되고, import 부작용에 의존하지 않기 위해서다. 검사는 세 가지다.

| 검사 | 금지하는 것 |
| --- | --- |
| `test_the_package_never_imports_a_broker_sdk` | `vmtrader/` 아래 어느 모듈도 벤더 SDK 최상위 모듈을 import하지 못한다 |
| `test_only_vendor_code_imports_vendor_code` | 벤더 고유 패키지(`vmtrader/broker/kis/`) 밖의 코드가 그것을 import하지 못한다 |
| `test_the_neutral_live_package_names_no_vendor` | 중립 라이브 패키지(`vmtrader/broker/live/`)는 벤더 이름을 아예 부르지 못한다 |

`from x import y`는 `x`와 `x.y`를 **둘 다** 검사 대상에 넣는다. 벤더 이름이 어느 쪽에 붙어 있어도 잡기 위해서다. 금지 목록(SDK 모듈명, 벤더 패키지 경로)은 그 테스트 파일 상단의 상수가 정본이다.

**왜 이 규칙이 있는가.**

- CI는 증권사 SDK를 설치할 수 없다. SDK가 배포 채널에 없고, 있어도 인증 파일을 요구한다.
- 설치할 수 있다 해도 테스트가 실계좌·실서버를 건드려서는 안 된다.
- 실패가 조용하다. SDK가 깔린 개발기에서는 아무 문제 없이 돌다가, SDK 없는 기계에서 백테스트를 돌리는 순간 `import` 단계에서 죽는다. 그래서 단언한다.

SDK를 실제로 부르는 코드는 저장소에 정확히 한 곳, `scripts/kis_gateway.py`뿐이다. 그 파일의 SDK import는 **함수 안**에 있어(`scripts/kis_gateway.py:453-454`) 모듈을 적재하는 것만으로는 SDK가 필요하지 않고, 그래서 `tests/unit/test_kis_gateway.py`가 SDK 없이 게이트웨이 로직 전체를 검증할 수 있다. 엔진은 SDK가 아니라 `BrokerClient` Protocol(`vmtrader/broker/live/client.py`)만 안다.

이 경계는 두 번째 증권사를 붙일 때의 비용도 정한다([ADR-0015](adr/0015-venue-neutral-live-package.md)) — 게이트웨이 파일 하나로 끝나는지, 포크가 되는지가 이 세 검사에 달려 있다.

## 3. 주입 규약

라이브 경로 테스트는 **실시간을 소비하지 않는다.** 대기·재시도·폴링을 검증하되 벽시계는 쓰지 않는다. 그래서 세 가지가 주입 가능하다.

| 주입 지점 | 위치 | 기본값 | 테스트가 넣는 것 |
| --- | --- | --- | --- |
| 가짜 `BrokerClient` | `LiveBroker`의 `client` 생성자 인자 (`vmtrader/broker/live_broker.py:96`) | 없음 — 필수 인자 | 호출 인자를 기록하고 미리 정한 `OrderReport` 시퀀스를 돌려주는 가짜 venue |
| 시계 | `vmtrader/broker/live_broker.py:126`, `vmtrader/trading/live.py:73` | 브로커는 자기 `current_dt`, 세션은 `pd.Timestamp.now` | 고정 타임스탬프 또는 **폴링 횟수로 전진하는 시계** |
| `sleep` | `vmtrader/broker/live_broker.py:580`·`:620`, `scripts/kis_gateway.py:151`·`:423` | 정산은 무동작 람다, 게이트웨이는 `time.sleep` | 잠든 시간을 리스트에 적립하는 콜러블(`tests/unit/test_kis_gateway.py:517`) |

세부 규약은 이렇다.

- **가짜 클라이언트가 표준이다.** 라이브 브로커의 단위 테스트도, 라이브 세션의 e2e도 모두 가짜 venue를 세운다. mock 라이브러리로 메서드를 패치하지 않는다 — Protocol이 계약이므로, 그 계약을 만족하는 작은 클래스를 테스트 파일 안에 쓰는 편이 계약 변경을 드러낸다.
- **시계는 사건에서 파생시킨다.** 데드라인 만료를 검증할 때 벽시계를 기다리지 않고, venue가 몇 번 폴링됐는지로 시각을 전진시킨다(`tests/unit/broker/test_live_broker.py:88`의 `_poll_driven_clock`). 시간이 흐르는 이유를 테스트가 통제한다.
- **정산의 기본 `sleep`은 무동작이다**(`vmtrader/broker/live_broker.py:620`). 테스트가 아무것도 넘기지 않아도 실시간 대기가 발생하지 않는다는 뜻이며, 이것이 기본값인 것 자체가 정책이다. 실제 간격은 운용 스크립트가 명시적으로 넘긴다(`scripts/kis_smoke.py:376`).
- **스레드별 자원도 주입된다.** SQLite 연결은 한 스레드에 묶이므로 워커가 메인 스레드의 연결을 빌릴 수 없고, `ledger_factory`(`vmtrader/broker/live_broker.py:135-136`)가 호출 스레드용 연결을 연다. 이 때문에 라이브 원장은 인메모리가 아니라 파일이어야 한다.
- **`time.sleep`·`pd.Timestamp.now`를 테스트가 monkeypatch하지 않는다.** 주입 지점이 있는데 패치하는 것은 계약을 우회하는 것이다. 새 라이브 코드가 시간을 필요로 하면 인자로 받아라.

## 4. 스레드 경계

라이브 경로에는 스레드가 정확히 하나 들어온다 — 정산 워커다([ADR-0008](adr/0008-task-queue-fill-pump.md)). 그 스레드가 존재해도 회계가 안전한 이유는 **불변식 하나** 때문이다.

> `Portfolio`·`Position`·엔진 시계·`Transaction` 생성은 **메인 스레드 전용**이다. 워커와 메인이 공유하는 상태는 락으로 보호된 체결 증분 버퍼와 스레드별 연결의 SQLite 원장, 둘뿐이다. ([`spec/kis-broker.md`](spec/kis-broker.md) NFR-8)

코드에서 이 불변식이 사는 곳은 세 지점이다.

| 지점 | 위치 | 역할 |
| --- | --- | --- |
| 워커 태스크 | `vmtrader/broker/live_broker.py:_poll_task` | venue를 폴링해 증분을 **버퍼와 원장에만** 넣는다. 포트폴리오를 만지지 않는다 |
| 드레인 배리어 | `settle()`의 `worker.join_tasks()` | 큐가 비기 전에는 회계로 넘어가지 않는다 |
| 단일 작성자 | `vmtrader/broker/live_broker.py:_drain_fill_buffer` (`:549`) | 메인 스레드에서만 `transact_asset`을 부른다 |

**테스트가 고정하는 것.**

| 성질 | 어디서 | 근거 |
| --- | --- | --- |
| 배리어는 타임아웃으로 포기되지 않는다 — 하트비트는 "말하기 위한" 것이지 "포기하기 위한" 것이 아니다 | `tests/unit/broker/test_live_broker.py`의 느린 드레인 테스트 | 배리어가 곧 단일 작성자 규율이다 |
| 드레인 배리어의 반환값은 큐를 보고 답한다 — 소비자가 없으면 `False` | `tests/unit/broker/live/test_worker.py` | `True`를 돌려주면 메인이 수집되지 않은 체결을 회계에 반영한다 |
| 종료는 절단이 아니라 소진이다 — 센티넬이 적재분 뒤에 들어가므로 수집된 체결이 유실되지 않는다 | 같은 파일 | — |
| 순서가 뒤바뀐 체결 확정이 포트폴리오 단조성 검사를 깨지 않는다 | `tests/unit/broker/test_live_broker.py` | 타임스탬프가 venue가 아니라 엔진 시계에서 나오기 때문이다([ADR-0007](adr/0007-engine-clock-timestamps.md)) |
| 접수 전건이 venue에 닿은 뒤에야 체결 수집이 시작된다 | `tests/integration/trading/test_live_session_e2e.py` | [ADR-0006](adr/0006-decouple-submit-from-fill.md) |
| **워커는 스레드를 남기지 않는다** — `stop()` 이후 살아있는 스레드 수가 이전과 같다. 종료 훅이 예외를 던져도 그렇다 | `tests/unit/broker/live/test_worker.py` | 워커는 리밸런싱 사이클에 종속된다. 상주 프로세스가 아니므로([ADR-0009](adr/0009-cron-oneshot-live-session.md)) 스레드가 남으면 cron 슬롯을 넘겨 프로세스가 끝나지 않는다 |
| 멈추지 않는 워커는 멈춘 척하지 않는다 — `stop()`이 시간 초과하면 `is_running()`이 계속 참이고 두 번째 소비자가 생기지 않는다 | 같은 파일 | 큐를 두고 경합하는 두 번째 스레드가 훨씬 나쁘다 |

워커는 **non-daemon**이다(`vmtrader/broker/live/worker.py:141`). 데몬 스레드는 인터프리터 종료 시 임의 지점에서 잘리므로, 원장에 쓰는 중인 스레드가 그렇게 죽으면 안 된다. 반대급부로 멈추지 않는 워커는 프로세스를 붙잡으며, 그래서 게이트웨이의 HTTP 타임아웃이 이 선택과 한 묶음이다(`tests/unit/test_kis_gateway.py:611` 이하 — 그 이유가 docstring에 적혀 있다).

다만 **`daemon=False`라는 플래그 자체를 단언하는 테스트는 없다.** 고정돼 있는 것은 그 결과(스레드가 남지 않는다)이며, 이는 `daemon=True`로 뒤집어도 통과한다. §9의 갱신 계기에서 이 간극을 다룬다.

백테스트 경로에는 스레드가 없다. 워커는 `LiveBroker` 내부 구현이며 `Broker` ABC에 나타나지 않는다.

## 5. 커버리지 정책

**하한의 정본은 [`../../.coveragerc`](../../.coveragerc)다.** 값은 여기 적지 않는다 — 옮겨 적는 순간 두 곳이 되고, 둘이 갈라지면 어느 쪽이 맞는지 알 수 없다. 이 문서가 적는 것은 그 하한이 **왜 그렇게 운용되는가**다.

| 규칙 | 근거 |
| --- | --- |
| 하한은 현재 실측보다 **약간 아래**에 둔다 | 줄 몇 개를 옮기는 리팩터링이 빌드를 깨지 않으면서, 실질적인 하락은 깨도록 하기 위해서다 |
| **낮추지 않는다** | 빨간 빌드를 초록으로 만들기 위해 하한을 내리는 것은 측정을 포기하는 것이다. 커버리지가 오르면 올린다 |
| 강제는 CI에서 일어난다 | [`../../.github/workflows/ci.yml`](../../.github/workflows/ci.yml)의 테스트 단계가 `fail_under`에 걸린다. 대시보드에서 나중에 발견되는 것이 아니라 그 자리에서 빌드가 깨진다 |
| 측정 범위는 `vmtrader/`다 | CI가 `--cov=vmtrader`로 부른다. `scripts/`는 테스트되지만 이 숫자에 들어가지 않는다 — 즉 커버리지 수치가 스크립트의 상태를 말해 주지 않는다 |
| 제외 규칙은 방어 코드에 한한다 | `pragma: no cover`와 `raise NotImplementedError`뿐이다. 도달 불가를 선언하는 것이지 미검증을 감추는 장치가 아니다 |

**라이브 신규 모듈에는 더 높은 기준이 적용된다**([`spec/kis-broker-design.md`](spec/kis-broker-design.md) §8). 이유는 비율 자체가 아니라 무엇을 덮었는지에 있다. 브로커 연동은 **실패 경로가 본질**이다 — 거절, 부분 체결, 데드라인 만료, 재기동, 중복 확정. 정상 경로만 덮은 커버리지는 이 코드에서 아무것도 보증하지 않는다. 설계안이 나열한 실패 모드 각각에 대응 테스트를 요구하는 것은 그래서다.

한 줄 요약: **커버리지가 높은 곳과 돈이 움직이는 곳이 일치해야 한다.** 실주문을 내는 코드와 그 부속이 가장 잘 덮여 있어야 하고, 남는 공백은 결과 보고 계층에만 있어야 한다.

### 5.1 의도적 커버리지 예외

아래 모듈은 **공백으로 남겨 두기로 판단한 것**이다. 잊힌 것이 아니다. 이 절이 없으면 다음 사람은 "왜 이것만 안 덮였는가"를 매번 다시 조사하고, 그때마다 같은 결론에 도달한다.

| 모듈 | 판단 | 근거 |
| --- | --- | --- |
| `vmtrader/statistics/tearsheet.py` | 공백 유지 | matplotlib 렌더링 계층이다. 단언 대상이 사실상 픽셀이고, 회계로 되먹임되지 않는다. 여기서 표시되는 지표는 전부 `statistics/performance.py`가 계산하며 그쪽은 단위 테스트로 덮여 있다 — 즉 **틀릴 수 있는 것은 이미 다른 곳에서 검증된다.** 인터페이스 완전성(`update`·`get_results`·`plot_results`·`save`)만 `tests/unit/test_abstract_base_classes.py`가 고정한다 |
| `vmtrader/statistics/json_statistics.py` | 공백 유지 | 결과 직렬화 계층이다. `vmtrader/` 안의 어떤 모듈도 이것을 import하지 않고, 유일한 사용처가 `scripts/static_backtest.py`다. 지표 계산은 `statistics/performance.py`에 위임하므로 자체 로직은 형태 변환에 가깝다 |
| `vmtrader/signals/vol.py` | 공백 유지 | **어디에서도 쓰이지 않는다.** 패키지·예제·스크립트 어느 조립 경로에서도 `VolatilitySignal`을 참조하지 않는다. 쓰이지 않는 코드에 테스트를 붙이는 것은 검증이 아니라 고정이다 |

**예외에서 나오는 조건**은 하나다 — 위의 근거가 깨지는 순간. 어떤 조립 경로가 `VolatilitySignal`을 실제로 쓰기 시작하면 그 커밋이 테스트를 함께 가져와야 한다. `json_statistics.py`가 스크립트 밖에서 불리기 시작해도 같다. 티어시트가 지표를 자체 계산하기 시작하면 그 계산은 `performance.py`로 가거나 테스트를 받는다.

**예외로 들어가는 조건**: 결과 보고·표현 계층이고, 회계에 되먹임되지 않으며, 실제로 틀릴 수 있는 계산이 테스트된 다른 모듈에 있을 것. 셋 중 하나라도 아니면 예외가 아니다. 회계·실행·주문 경로는 어떤 이유로도 이 표에 들어가지 않는다.

## 6. e2e 안전망의 범위와 한계

`tests/integration/trading/test_backtest_e2e.py`는 백테스트 전 거래 이력을 `tests/integration/trading/fixtures/*.dat`와 `assert_frame_equal`로 **완전 일치** 대조한다. 이것이 이 저장소에서 가장 강한 회귀 안전망이다. 강한 만큼 무엇을 증명하지 **않는지**를 알아야 한다.

| 증명하는 것 | 증명하지 않는 것 |
| --- | --- |
| 체결 계층의 어떤 변화도 이력에 나타난다 — 수량 절사 규칙, 매도 선행 정렬, 개장 판정, 현금 버퍼 | 그 이력을 만들어 낸 **정책이 옳은가** |
| 리팩터링이 동작을 바꾸지 않았다 | 리팩터링 이전의 동작이 맞았다 |
| 조립 경로가 실제로 연결돼 있다 | 조립되지 않은 대안 경로 |

**한계는 구조적이다.** 기준 `.dat` 파일은 현재 구현을 돌려서 생성됐다. 그러므로 구현이 틀린 채로 생성됐다면 기준 파일도 같은 방식으로 틀리고, 대조는 영원히 일치한다. 완전 일치 대조는 **변화**를 잡지 **오류**를 잡지 않는다.

[보고서 20260818-06](reports/20260818-06-safety-net-and-profiling.md)이 변형 주입으로 이 성질을 실측했다(수치는 그 보고서에 있다). 가장 중요한 결과는 이것이다.

> **가격 조회를 직전 값에서 직후 값으로 바꿔 전면적인 룩어헤드를 주입해도 e2e 테스트는 통과한다.**

백테스트 엔진에서 상상할 수 있는 가장 심각한 부류의 오류가 안전망을 그대로 지나간다. 원인은 안전망의 부실이 아니라 **조회 지점의 성질**이다 — 그 픽스처가 만드는 입력이 해당 정책을 실행하지 않는다. 통합 테스트는 "조립이 돌아간다"를 증명할 뿐, 조립된 부품 각각의 규칙을 실행해 주지는 않는다. 성과지표 계산식이나 수수료 배율을 훼손해도 마찬가지로 e2e는 조용하고, 그것들을 잡은 것은 단위 테스트다.

따라서 정책은 다음과 같다.

- **통합 테스트는 단위 테스트를 대체하지 못한다.** e2e가 통과했다는 것은 근거가 아니다.
- 새 정책(가격 조회 방식, 비용 규칙, 사이징 규칙)을 넣으면 **그 정책을 실행하는 입력**을 가진 단위 테스트를 함께 넣는다.
- 기준 `.dat` 파일을 갱신하는 커밋은 **왜 이력이 달라져야 하는지**를 커밋 메시지에 적는다. 기준 파일 갱신은 안전망을 끄는 행위이므로, 근거 없이 다시 생성하지 않는다.

## 7. 테스트를 명세로 읽기

이 저장소의 여러 계약은 산문이 아니라 테스트에 적혀 있다. 라이브 브로커의 계약, 손익 회계 규칙, 워커 수명주기, 대조의 비대칭 — 전부 해당 테스트 파일이 사실상 유일한 명세다.

**어느 계약이 어느 테스트에 대응하는가는 [`architecture-map.md`](architecture-map.md) §5의 "계약 ↔ 테스트 링크 표"가 정본이다.** 여기서 되풀이하지 않는다. 이 절이 정하는 것은 **그렇게 쓸 때의 규칙**이다.

| 규칙 | 왜 |
| --- | --- |
| **계약을 바꾸면 테스트를 먼저 고친다.** 구현을 고친 뒤 테스트를 맞추면, 그 테스트는 계약을 진술하는 것이 아니라 구현을 받아 적는 것이 된다 | 명세로 읽히는 문서가 구현을 뒤따라가면 명세가 아니다 |
| **테스트 docstring에는 "무엇을"이 아니라 "왜"를 쓴다.** 이 저장소의 관례는 그 테스트가 막으려는 사고를 적는 것이다 | `test_worker.py`나 `test_vendor_import_boundary.py`를 열면 각 단언이 어떤 실패를 겪고 생겼는지 읽힌다. 삭제해도 되는 테스트인지 판단할 수 있는 유일한 근거다 |
| **결정에서 나온 테스트는 docstring에 ADR 번호를 적는다** | 예: `tests/unit/broker/test_live_broker.py:129`(ADR-0006), `tests/unit/test_abstract_base_classes.py:213`(ADR-0016). ADR을 뒤집을 때 무엇이 깨질지가 검색으로 나온다 |
| **요구사항에서 나온 테스트는 FR/NFR 번호나 인수기준을 적는다** | 예: `tests/integration/trading/test_live_session_e2e.py:4`(인수기준 A-1). 스펙이 갇혀 있는 문서에서 테스트로 오는 유일한 다리다 |
| **결함을 지금 고치지 않기로 했다면, 현재 동작을 고정하는 테스트를 쓰고 docstring에 "이것은 결함이다"라고 적는다** | 고치지 않은 결함이 조용히 정상 동작으로 승격되는 것을 막는다 |
| **인터페이스 목록을 고정하는 테스트는 목록 자체가 계약이다** | `tests/unit/test_abstract_base_classes.py`의 ABC 목록·추상 메서드 집합이 그렇다. ABC를 늘리거나 추상 메서드를 빼면 이 파일이 같은 커밋에서 바뀌어야 한다 |

읽는 순서는 이렇다. **ADR → 그 ADR이 만든 테스트 → 구현.** 구현부터 읽으면 "왜 이렇게 복잡한가"에 답이 없다. 학습 경로 전체는 [보고서 20260823-01](reports/20260823-01-codebase-comprehension-strategy.md)에 있다.

## 9. 이 문서의 갱신 규칙

**갱신은 같은 커밋에서 한다.** 아래 변경 중 하나라도 하면서 이 문서를 손대지 않으면, 그 커밋은 문서를 틀리게 만든 커밋이다.

| 갱신 계기 | 이 문서에서 손볼 곳 |
| --- | --- |
| `.coveragerc`의 하한을 바꾼다 | §5 — 값이 아니라 **규칙과 근거**가 여전히 맞는지. 낮추는 경우라면 왜 규칙의 예외인지를 적는다 |
| 새 경계 테스트를 추가한다(import 경계, 인터페이스 목록 등) | §1 계층 표, §2 검사 표 |
| `tests/` 계층 구조를 바꾼다(미러링 규칙, 통합 테스트의 단위, conftest 배치) | §1 전체 |
| 의도적 커버리지 예외가 늘거나 준다 | §5.1 — 들어가면 근거를, 나오면 행을 지운다 |
| 주입 규약을 바꾼다(새 주입 지점, 기본값 변경, 주입 지점 제거) | §3 표. 파일:줄이 어긋나면 고친다 |
| ABC 목록이나 추상 메서드 집합이 바뀐다 | §7 마지막 규칙 — 인터페이스 목록 고정 테스트가 계약이라는 진술이 유지되는지 |
| 스레드 경계 불변식이 바뀐다(작성자 추가, 공유 상태 추가) | §4 전체. 이것은 ADR도 함께 필요한 변경이다 |
| e2e 기준 `.dat`를 다시 생성한다 | §6 — 한계 진술이 여전히 맞는지 |
| CI가 강제하는 것이 바뀐다(린트 추가, 게이트 추가) | §5 강제 행, §8 링크 표 |

**폐기(deprecation) 규칙은 없다.** 이 문서는 살아있는 문서이므로, 틀린 절은 취소선이나 "구버전" 표기 없이 **지우고 고쳐 쓴다.** 이전 내용은 git 이력에 있다.

이것은 [`adr/`](adr/)와 정반대다. ADR은 결정이 뒤집혀도 본문을 고치지 않고 새 ADR을 쓴 뒤 기존 문서를 `Superseded`로 표시한다 — 그때 무엇을 알고 무엇을 결정했는지가 기록의 값이기 때문이다. [`reports/`](reports/)도 같은 이유로 본문을 갱신하지 않는다. 반면 이 문서의 값은 **지금 무엇이 강제되고 있는가**에 있고, 낡은 진술은 값이 아니라 오류다.
