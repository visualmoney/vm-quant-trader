## 1. 요약

네 가지 물음에 답한다. **앞의 둘은 현행 설계의 확인이고, 뒤의 둘은 전제가 바뀔 때의 재검토다.**

| # | 물음 | 답 |
| --- | --- | --- |
| Q1 | smtm의 `Worker`는 daemon인데 `TaskQueueWorker`는 왜 non-daemon인가 | **프로세스 모델이 다르기 때문이다.** smtm은 상주 데몬이라 워커에게 종료를 인질로 잡히면 안 되고, vmtrader는 cron 단발이라 워커가 프로세스보다 오래 살 수 없다. daemon일 이유가 사라진 자리에 "체결 유실 0"과 "회계 단일 작성자 배리어"라는 이득만 남는다 |
| Q2 | 신호(`SIGINT`/`SIGTERM`)를 받으면 어떻게 되는가 | 핸들러가 **한 건도 없다.** `SIGINT`는 `finally`를 태워 정리하고 나가며(실측 exit 130), `SIGTERM`은 정리 없이 즉사한다(실측 exit 143). **어느 쪽도 데이터를 손상시키지 않는다** — 유실되는 것은 전부 매 기동 재구성되는 메모리 상태다 |
| Q3 | 사이클이 10~20분으로 길어져도 non-daemon이 맞는가 | **맞다.** 실행 시간은 daemon 여부의 판단 근거가 아니다. 길어지면서 커지는 것은 **hang이 cron 슬롯을 점유하는 비용**이며, 그 해법은 daemon 플래그가 아니라 **프로세스 바깥의 실행 시간 상한**이다 (§5) |
| Q4 | 텔레그램이 리밸런싱을 강제 수행한다면 | **트레이딩을 별도 프로세스로 띄우는 A안이면 무변경**이다. 게이트웨이 안에서 엔진을 돌리는 B안을 택하면 daemon 논쟁만 재개되는 것이 아니라 `max_orders_per_session`·`trading_halted`처럼 **"프로세스 = 세션"에 박혀 있던 전제 여러 개가 동시에 깨진다** (§6) |

부수적으로 다음 둘을 함께 다룬다.

- **신호 핸들러 도입은 범위 안인가** — 트레이딩 평면은 범위 밖, 게이트웨이 데몬은 범위 안, B안이면 필수다 (§7).
- **cron 대신 systemd** — 상주 게이트웨이에는 명백히 옳고, 트레이딩 단발에도 timer가 cron보다 낫다. 다만 **"죽으면 재시작"은 트레이딩 평면에 그대로 이득이 아니다** (§8).

가장 중요한 실측 결과는 §5.2다. **`stop()`에 타임아웃을 주는 것만으로는 hang이 풀리지 않는다** — non-daemon 스레드는 인터프리터 종료에서 다시 프로세스를 붙든다.

## 2. 두 워커의 대조

구조는 같다. 스레드 1개, FIFO `queue.Queue`, `None` 센티넬 종료. 다른 것은 **수명**과 **실패했을 때의 태도**이며, daemon 플래그는 그 차이의 결과다.

| 항목 | smtm `Worker` | vmtrader `TaskQueueWorker` |
| --- | --- | --- |
| 스레드 종류 | `daemon=True` (`worker.py:82`) | `daemon=False` (`worker.py:78-80`) |
| 수명 | 애플리케이션 수명 — 오퍼레이터·트레이더·텔레그램 송신이 각자 상주 워커를 갖는다 | **리밸런싱 사이클 1회** — `settle()` 안에서 생성되어 같은 함수에서 사라진다 (`kis_broker.py:648`, `:676`) |
| `stop()` | 센티넬 투입 후 `task_queue.join()` — **스레드 자체는 join하지 않는다** (`worker.py:85-95`) | 센티넬 투입 후 `thread.join(timeout)` — 스레드의 소멸까지 기다린다 (`worker.py:131-132`) |
| 태스크 예외 | `UserWarning`을 올리며 **워커가 죽는다.** 이후 `post_task`는 조용히 쌓이기만 한다 (`worker.py:76-80`) | `on_error` 콜백으로 보고하고 **다음 태스크를 계속 소화한다** (`worker.py:72-76`) |
| 스레드 경계 | 콜백이 스레드를 넘는다 — 트레이더 워커에서 전략 상태를 갱신한다 (`trading_operator.py:101-105`) | 워커는 회계를 만지지 않는다 — 락 버퍼와 스레드별 원장 연결뿐, 기표는 메인 스레드 (ADR-0008, NFR-8) |
| 종료 신호 | `signal.signal(SIGINT/SIGTERM)` → `operator.shutdown()` (`telegram_controller.py:77-78`) | **핸들러 없음** — 저장소 전체에 `signal` 등록 0건 |

## 3. Q1 — non-daemon을 택한 이유

결정 자체는 ADR-0008에 명시되어 있다: **"daemon=False, 상주 금지"**. 근거는 세 층이다.

### 3.1 프로세스 모델이 다르다

smtm의 메인 스레드는 `time.sleep(0.5)` 루프를 돌 뿐이고 실제 일은 전부 워커에서 벌어진다(`telegram_controller.py:82-83`). 이런 프로그램에서 워커가 non-daemon이면 **종료가 워커의 협조에 인질로 잡힌다** — 어느 한 워커가 큐에서 깨어나지 못하면 프로세스가 나가지 못한다. 그래서 `daemon=True`가 옳고, 대신 종료 시각을 사람이 지정해 주기 위해 신호 핸들러가 필요해진다.

vmtrader는 정반대다. ADR-0009가 라이브 세션을 **cron 단발**로 못박았다 — 기동 1회 = 사이클 1회. 워커의 수명이 프로세스 수명보다 짧으므로 "워커가 종료를 막는다"는 문제 자체가 성립하지 않는다.

### 3.2 유실 0의 종료 시퀀스가 요구사항이다

워커 태스크는 KIS 체결 조회 → 원장(SQLite) 기록 → 락 버퍼 적재를 한 묶음으로 수행한다(`kis_broker.py:556-582`). daemon 스레드는 인터프리터 종료 시 **임의의 지점에서** 사라진다. non-daemon + `stop()`의 join은 "수집했지만 아직 넘겨주지 않은 체결이 종료 경로에서 버려지는 일은 없다"를 언어 차원에서 보장한다.

### 3.3 회계의 단일 작성자 규율과 짝을 이룬다

`Portfolio`는 락이 없고 타임스탬프 단조성에 민감하다. 메인 스레드가 **join으로 워커의 소멸을 확인한 뒤** 버퍼를 드레인하기 때문에 배리어가 성립한다. 데몬 스레드가 배경에서 계속 살아 있는 모델이라면 "드레인 이후에 도착한 체결"이라는 애매한 상태가 생긴다.

> 요컨대 이 선택은 취향 차이가 아니라 **ADR-0009(단발) → ADR-0008(사이클 수명 워커) → non-daemon**으로 이어지는 한 줄기 결론이다. 전제가 바뀌면(§6 B안) 재검토 대상이 된다.

## 4. Q2 — 신호가 도착하면 실제로 어떻게 되는가

저장소 전체에 `signal.signal` 등록도, `atexit` 훅도, `KeyboardInterrupt`를 다루는 코드도 없다. 따라서 동작은 전적으로 CPython의 기본 처분과 `settle()`의 `try/finally` 배치가 결정한다.

아래는 실제 `TaskQueueWorker`에 2초짜리 태스크 3개(= 미결 주문 3건 1회차)를 적재하고 0.5초 뒤 신호를 보낸 **실측**이다.

### 4.1 SIGINT — 정리하고 나가지만 즉시는 아니다

```text
0.00s task 0 start
0.50s main caught 'KeyboardInterrupt'      ← settle()의 join_tasks()에서 탈출
0.50s finally: stop()                      ← 센티넬은 큐 맨 뒤
2.00s task 0 end
2.00s task 1 start                         ← 이미 적재된 폴링은 계속 나간다
4.00s task 1 end
4.00s task 2 start
6.00s task 2 end
6.00s finally: stopped                     ← 인터럽트로부터 5.5초
KeyboardInterrupt (exit 130)
```

센티넬을 **큐의 뒤**에 넣는 것은 의도된 설계다(`worker.py:117-122`). 그 대가로 Ctrl-C의 체감 지연은 **그 회차에 적재된 미결 주문 수 × 조회 1회 시간**이 된다. 게이트웨이가 모의계좌에서 호출 간 최소 0.7초를 강제하므로(`kis_gateway.py:52` `MIN_CALL_INTERVAL`), 세션 상한인 20건이 미결이면 십수 초 규모다.

**Ctrl-C를 두 번 눌러도 빨라지지 않는다.** 두 번째 `KeyboardInterrupt`는 `stop()`의 join을 탈출시키지만, 센티넬은 이미 큐에 있으므로 기다림이 인터프리터 종료 시의 non-daemon join으로 옮겨갈 뿐이다(실측: 총 소요 동일, exit 0).

### 4.2 SIGTERM — 정리 코드가 한 줄도 돌지 않는다

```text
0.00s task 0 start
Terminated                                 ← finally 미실행, 워커 태스크 중단
exit 143
```

### 4.3 미결 주문의 STALE 기록은 건너뛴다

`settle()`에서 미결 주문을 `STALE`로 닫는 루프는 `try/finally` **바깥**에 있다(`kis_broker.py:678-686`). `KeyboardInterrupt`가 전파되면 이 루프는 실행되지 않아 원장에 주문이 `SUBMITTED`로 남는다. 손상은 아니다 — 다음 기동의 `reconcile()`이 "이전 프로세스가 열어 둔 주문"을 거래소와 대조해 정리하는 것이 정상 경로이며(`reconcile.py:129-176`), 운용 문서도 *"멈추면 미체결 주문은 취소하지 않는다"*를 방침으로 명시한다(`docs/user/kis-live-operations.md` §6).

### 4.4 무엇이 남고 무엇이 사라지나

| 상태 | 매체 | SIGINT | SIGTERM / SIGKILL | 회복 경로 |
| --- | --- | --- | --- | --- |
| 체결 기록 | 원장 SQLite | 보존 | 보존 (write마다 commit) | — |
| 미기표 체결 버퍼 | 메모리 | 드레인됨 | **유실** | 다음 기동 `update()`가 흡수 |
| 포트폴리오 | 메모리 | 유실 | 유실 | 매 기동 잔고에서 재구성 (정상 경로) |
| 미결 주문 | 거래소 + 원장 | `SUBMITTED` 잔존 | `SUBMITTED` 잔존 | `reconcile()`이 대조·정리 |
| 자본곡선 1행 | 원장 | EOD 기동이 별도로 기록 — 리밸런싱 기동이 죽어도 남는다 | 〃 | — |
| flock 잠금 | 파일 락 | 해제 | 해제 (프로세스 소멸 시 OS가) | — |

**신호로 인한 데이터 손상은 설계상 존재하지 않는다.** 이것이 핸들러 없이도 버티는 이유이며, 동시에 핸들러를 추가할 유인이 약한 이유이기도 하다.

## 5. Q3 — 10~20분 사이클에서도 non-daemon이 맞는가

### 5.1 실행 시간은 판단 근거가 아니다

daemon 여부를 가르는 물음은 "얼마나 오래 도는가"가 아니라 **"스레드가 프로세스보다 오래 살 수 있는가"**다. 사이클이 20분이 되어도 워커는 여전히 `settle()` 안에서 태어나 같은 함수에서 죽는다. 구조가 바뀌지 않으므로 결론도 바뀌지 않는다.

길어지면서 실제로 달라지는 것은 셋이다.

1. **신호가 도착할 확률** — 호스트 재부팅·OOM killer·운용자 `kill`이 사이클과 겹칠 창이 넓어진다.
2. **hang의 비용** — 무한 대기가 `flock` 잠금을 점유하는 시간이 길어져, 같은 잠금을 쓰는 EOD 기동까지 막을 수 있다.
3. **Ctrl-C 드레인 지연** (§4.1) — 미결 주문이 많을수록 길어진다.

셋 다 daemon 플래그가 아니라 **실행 시간 상한**으로 다루는 문제다.

### 5.2 두 손잡이는 독립이다 — 실측

- `daemon` = **인터프리터가 종료 시 이 스레드를 기다리는가**
- `stop()`의 join = **정상 경로에서 우리가 기다리는가**

vmtrader가 원하는 것은 "정상 경로는 기다린다(유실 0) + 병리 경로는 슬롯을 잡아먹지 않는다"이다. 워커가 타임아웃 없는 소켓에 30초 갇힌 상태를 만들고 네 조합을 측정했다.

| `stop()`의 join | `daemon=False` (현행) | `daemon=True` |
| --- | --- | --- |
| **무한 (현행)** | 영구 hang | 영구 hang (join이 무한이므로 동일) |
| **유한 (2초)** | join은 2.2초에 반환하지만 **인터프리터 종료에서 다시 막힌다** — 프로세스가 못 나감 (실측 exit 124) | 2.2초에 정상 종료 (실측 exit 0). 대가는 그 태스크 1건의 유실 |

**여기서 얻는 교훈이 이 보고서에서 가장 실용적인 부분이다.** `stop()`에 타임아웃을 주는 것은 *진단*(로그가 남는다)일 뿐 *종료 보장*이 아니다. non-daemon을 유지하는 한 종료 보장은 **프로세스 바깥**에서 와야 한다.

### 5.3 그런데 `daemon=True`는 반쪽 backstop이다

메인 스레드도 같은 SDK를 호출한다 — 주문 접수, `reconcile`, 시세 조회 전부. `open-trading-api`의 `kis_auth.py:443-445`는 `requests.get/post`를 **`timeout=` 없이** 호출하므로, 갇히는 것이 워커가 아니라 메인 스레드일 수 있다. 그 경우 daemon 플래그는 아무 도움이 되지 않는다.

> **결론 (Q3)**: 10~20분에서도 **non-daemon을 유지한다.** 조치는 플래그 변경이 아니라 ⓐ 프로세스 실행 시간 상한(§8의 systemd 또는 `timeout -k`), ⓑ 진단용 유한 join + 초과 로그, ⓒ F-2의 한 줄 수정이다.

## 6. Q4 — 텔레그램이 리밸런싱을 강제 수행할 때

이 전제는 ADR-0009의 "프로세스 수명 = 사이클 수명"을 건드리므로 배선에 따라 답이 갈린다.

### 6.1 A안 (권고) — 게이트웨이는 방아쇠만 당긴다

게이트웨이는 트레이딩을 **자기 프로세스 안에서 돌리지 않고**, cron이 쓰는 것과 같은 실행 단위를 띄운다.

```python
# 게이트웨이의 "지금 리밸런싱" 명령 처리 — vmtrader/pandas를 import하지 않는다
proc = subprocess.Popen([
    'flock', '-n', LOCK, '--',
    'systemd-run', '--user', '--unit=vmtrader-rebalance-adhoc', ...   # 또는 run_live.sh
])
```

- **트레이딩 평면은 여전히 단발**이므로 ADR-0008·0009는 무변경이고, non-daemon 워커도 그대로 정답이다.
- NFR-8(스레드 경계)이 애초에 문제가 되지 않는다 — 게이트웨이 프로세스는 `Portfolio`에 닿지 않는다.
- 게이트웨이가 pandas·vmtrader를 import하지 않으므로 ADR-0010의 **상주 RSS 80MiB 상한**이 유지된다.
- cron 기동과의 겹침은 **같은 잠금 파일**로 배제되고, `flock -n`의 종료코드 1이 그대로 "이미 실행 중입니다" 응답이 된다.
- **트레이딩이 죽어도 채팅 평면은 살아 있다** — 사고 중에도 킬스위치를 걸 수 있다는 뜻이며, 이 성질 하나만으로도 A안이 B안보다 낫다.

진행 상황 보고는 ADR-0010이 이미 정한 대로 **원장 읽기 전용**으로 한다. 20분짜리 사이클에서는 이 편이 오히려 자연스럽다 — 원장의 `orders`·`fills` 행이 곧 진척도다.

### 6.2 B안 — 게이트웨이 안에서 엔진을 돌린다 (smtm 배선)

여기서만 daemon 논쟁이 재개된다. 그런데 재검토해야 할 것은 daemon 플래그만이 아니다. **"프로세스 = 세션"이라는 전제에 기대고 있던 코드가 여러 곳에서 조용히 깨진다.**

| 깨지는 전제 | 코드 | 상주 전환 시 증상 |
| --- | --- | --- |
| 세션 주문 상한의 리셋 지점 | `guards.py:59` — `orders_submitted`는 `__init__`에서만 0이 된다 | "세션"이 하루가 아니라 **데몬 수명**이 되어, 두 번째 강제 리밸런싱이 `max_orders_per_session`에 막힌다 |
| 거래 중단의 해제 지점 | `kis_broker.py:124`·`:473`, `reconcile.py:127` — `trading_halted`는 True로만 바뀐다 | 일시적 대조 불일치 한 번이 **재기동 전까지 영구 halt**가 된다 |
| 명령 실행 스레드 | smtm은 폴링 스레드에서 오퍼레이터 상태를 만진다 (`telegram_controller.py:85-96`) | NFR-8 위반. 명령 큐 → 메인 루프 실행으로 재설계해야 한다 (ADR-0010 규칙 4가 이미 이식 금지로 못박은 부분) |
| 단일 사이클 가정 | `flock`은 프로세스 간에만 유효 | cron 기동과 채팅 트리거가 **한 프로세스 안에서** 겹칠 수 있다 → 인프로세스 뮤텍스 추가 필요 |
| 자원 | pandas import만 66MiB, 엔진 피크 NFR-9 400MiB, 호스트 가용 260~590MiB | ADR-0010 대안 1이 이미 "가능하나 권고 불가"로 기각한 지점 |
| 토큰 수명 | C-2, 24시간 만료 | 장중 갱신 경로를 새로 만들어야 한다 |

B안을 택한다면 워커는 **여전히 non-daemon이어야 하지만**(체결을 기표 전에 잃으면 안 되는 것은 그대로), `stop()`의 유한 join은 **선택이 아니라 필수**가 된다 — 데몬 전체가 한 사이클의 폴링에 인질로 잡히면 안 되기 때문이다.

### 6.3 어느 안이든 지금 없는 것: 강제 경로 자체

현행 `LiveTradingSession.run_rebalance()`는 **리밸런싱 날이 아니면 아무것도 하지 않고 반환한다**(`live.py`의 `_is_rebalance_day`). 채팅으로 "지금 리밸런싱"을 시켜도 조용히 무시되는 형태다. 강제 경로는 `rebalance_dates=None`인 세션을 만들거나 명시적 인자를 받아야 한다.

단, **강제라도 우회해서는 안 되는 것**이 있다 — 킬스위치(`guard.check_can_trade`)와 `reconcile`의 halt다. 그 둘은 "오늘 거래하기로 했는가"가 아니라 "거래해도 안전한가"를 판정하므로 강제의 대상이 아니다.

## 7. 신호 핸들러 도입은 범위 안인가

**평면마다 답이 다르다.**

| 평면 | 핸들러 | 근거 |
| --- | --- | --- |
| **트레이딩 (cron/timer 단발, 현행)** | **범위 밖 — 도입하지 않는다** | 정식 중단 수단은 이미 HALT 플래그 파일이다(FR-19). 프로세스가 항상 떠 있지 않으므로 신호로는 세션 사이에 멈출 수 없고, 파일이면 세션 중이든 사이든 동일하게 동작한다. §4.4가 보이듯 즉사해도 손상이 없으므로 핸들러가 사는 이득은 "STALE 한 줄"뿐이고, 대신 종료 경로 코드와 그 경로의 테스트라는 지속 비용이 생긴다 |
| **게이트웨이 데몬 (ADR-0010, A안)** | **범위 안 — 다만 경량으로** | 상주 프로세스는 자기 종료를 소유해야 한다는 smtm의 논리가 그대로 적용된다. 다만 게이트웨이의 상태는 원장 읽기 전용 + 플래그 파일뿐이라 핸들러는 `terminating = True` 한 줄이면 충분하다. systemd `Restart=always`와 함께 쓰면 종료-재기동이 관측 가능해진다 |
| **엔진 상주 (B안)** | **필수** | smtm이 핸들러를 둔 이유가 그대로 성립한다. 단 핸들러는 **플래그만 세우고**, `settle()`의 감시 루프가 킬스위치를 확인하는 자리에서 함께 회수해야 한다 |

**smtm의 구현을 그대로 이식하지는 않는다.** `_terminate`는 시그널 핸들러 안에서 오퍼레이터 종료와 텔레그램 송신까지 수행한다(`telegram_controller.py:98-106`). 핸들러 안의 네트워크 I/O와 join은 재진입·데드락의 고전적 자리이고, 핸들러가 예외를 내면 종료 자체가 실패한다. 이식할 것은 **"상주 프로세스가 종료 시각을 소유한다"는 사고**이지 그 배선이 아니다 — ADR-0010 규칙 4가 다른 대상에 대해 이미 같은 취지를 말하고 있다.

## 8. cron 대 systemd

> 지적대로 systemd에는 cron에 없는 **감독(supervision)**이 있다. 다만 그 이득은 평면마다 크기가 다르고, 트레이딩 평면에서는 **그대로 이득이 아니다.**

### 8.1 게이트웨이 데몬 — systemd가 명백히 옳다

cron으로는 상주 프로세스를 감독할 수 없다. `Restart=always`·`RestartSec`·`journalctl` 통합에 더해, **`MemoryMax=80M`은 ADR-0010이 규칙으로만 적어 둔 RSS 상한을 커널이 강제하게 만든다.** 이것은 문서가 할 수 없는 일이다.

```ini
# vmtrader-telegram.service  (게이트웨이 — 상주)
[Service]
Type=exec
ExecStart=/home/ec2-user/vm-quant-trader/.venv/bin/python scripts/telegram_gateway.py
Restart=always
RestartSec=5
MemoryMax=80M
TimeoutStopSec=10
```

### 8.2 트레이딩 단발 — timer가 cron보다 낫다, 이유는 재시작이 아니다

systemd timer의 이득은 "죽으면 재시작"이 아니라 이쪽이다.

| 이득 | 무엇을 대체하는가 |
| --- | --- |
| **실행 시간 상한** | §5의 hang 대책 — `timeout -k` 래퍼를 유닛 파일 한 줄로 대체한다 |
| 동일 유닛 중복 실행 방지 | `flock -n` (동거 봇과 공유하는 잠금이 아니라면) |
| 실패 상태의 영속화 | `systemctl status` / `journalctl -u` — cron의 "메일 아니면 로그 파일" 대신 |
| `MemoryMax=400M` | NFR-9를 커널이 강제 |

**주의할 systemd의 함정 두 가지** (systemd 255 매뉴얼 확인):

- `RuntimeMaxSec=`은 **`Type=oneshot`에 효과가 없다.** oneshot은 활성화 완료와 동시에 종료한 것으로 취급되기 때문이다. oneshot에서 실행을 자르려면 **`TimeoutStartSec=`**를 써야 한다(oneshot에서는 기본값이 무제한).
- `Restart=always`·`on-success`는 **`Type=oneshot`에서 거부된다.** oneshot은 정상 종료 시 재시작되지 않으며, `on-failure`만 의미를 갖는다.

```ini
# vmtrader-rebalance.service
[Service]
Type=oneshot
TimeoutStartSec=3600          # ← 무한 hang의 유일한 상한 (RuntimeMaxSec은 oneshot에 무효)
ExecStart=/home/ec2-user/vm-quant-trader/.venv/bin/python -m scripts.run_live rebalance
Restart=no                    # ← §8.3
MemoryMax=400M
Environment=TZ=Asia/Seoul
```

```ini
# vmtrader-rebalance.timer
[Timer]
OnCalendar=Mon..Fri 10:00     # 타임존 접미사는 systemd v252+ — 호스트 버전 확인 후 사용
Persistent=false              # ← §8.4
```

`TimeoutStartSec` 만료 시 systemd는 `SIGTERM`을 보낸다. **핸들러가 없으므로 프로세스는 즉사하고**(§4.2), 잠금과 슬롯이 곧바로 회수된다 — 여기서는 핸들러의 부재가 오히려 종료를 확실하게 만든다.

### 8.3 "죽으면 재시작"은 리밸런싱에 그대로 적용하면 안 된다

크래시한 리밸런싱을 자동으로 재실행하면 **사이클이 처음부터 다시 돈다.** 재기동 경로는 잘 설계되어 있지만(FR-7), 한 가지 구멍이 있다.

`reconcile()`은 원장이 열어 둔 주문을 거래소와 대조하고, **아직 체결되지 않은 주문은 `open_orders`에 그대로 남긴다**(`reconcile.py:163-171` — 종결된 주문만 `resolved`로 닫힌다). 반면 사이저는 **거래소 잔고**에서 목표를 다시 계산하므로, 거래소에서 아직 일하고 있는 미체결 주문은 목표 계산에 반영되지 않는다. 결과적으로 **같은 의도에 대해 두 번째 주문이 나갈 수 있다.**

- 방어가 완전히 없지는 않다 — 주문번호가 없는 접수(orphan intent)와 보유 과대는 `trading_halted`로 거래를 멈춘다(`reconcile.py:118-127`).
- 그러나 "미체결로 살아 있는 주문"은 그 두 경우 어디에도 걸리지 않는다.

따라서 **리밸런싱 유닛은 `Restart=no`**를 권고한다. 실패는 journal과 `systemctl status`에 남고, 재시도 여부는 사람(또는 텔레그램)이 판단한다. 반대로 **EOD 유닛은 조회·기록만 하므로 `Restart=on-failure` + `RestartSec=300` + `StartLimitBurst=3`이 안전**하다.

### 8.4 `Persistent=true`(놓친 실행 따라잡기)는 리밸런싱에서 끄는 것을 권고한다

cron에 없던 기능이지만, ADR-0009는 10:00을 **슬리피지 근거로** 골랐다. 재부팅 후 13:20에 따라잡아 시장가로 리밸런싱하면 그 근거가 무너진다. 하루를 건너뛰는 편이 낫다(다음 리밸런싱이 흡수한다). EOD는 반대로 `Persistent=true`가 유용하다 — 목적이 자본곡선 한 행이고 시각 민감도가 낮다.

### 8.5 도입 비용

호스트의 동거 봇 전원이 `cron + flock` 관례이고(ADR-0009 근거 C-15), systemd 유닛 설치에는 root 또는 `loginctl enable-linger` + user 유닛이 필요하다. **관례에서 벗어나는 비용**은 실재하므로, 최소 도입안은 이 순서를 권고한다.

1. 게이트웨이(상주)만 systemd로 — cron으로는 아예 불가능한 것부터.
2. 트레이딩은 cron을 유지하되 `flock` 안쪽에 `timeout -k 30 3600`을 넣어 §5의 hang을 먼저 막는다.
3. timer 이전은 그다음 — 얻는 것은 주로 관측성이며, 위 두 가지가 끝난 뒤에도 남는 이득만큼만 하면 된다.

## 9. 소견

| ID | 소견 | 심각도 |
| --- | --- | --- |
| **F-1** | 종료가 영영 끝나지 않을 수 있는 경로가 둘 있다 | **위험** |
| **F-2** | `worker.start()`가 `try` 바깥에 있다 | 주의 |
| **F-3** | SIGINT 경로에서 STALE 기록만 빠진다 | 경미 |
| **F-4** | 트레이딩 평면의 SIGTERM 핸들러는 도입하지 않는 쪽을 권고 | 설계대로 |
| **F-5** | `join_tasks()`의 timeout 분기에 죽은 코드 | 경미 |
| **F-6** | 강제 리밸런싱 경로가 없다 | 주의 |
| **F-7** | 상주 전환 시 `max_orders_per_session`·`trading_halted`의 리셋 지점이 사라진다 | **위험** (B안 한정) |
| **F-8** | 크래시 자동 재시작은 미체결 주문을 이중으로 낼 수 있다 | **위험** (자동 재시작 도입 시) |
| **F-9** | `task_done()`의 위치가 드레인 배리어의 의미를 정한다 — smtm은 2022년에 그 의미를 잃었다 | 주의 (회귀 함정) |

### F-1 · 종료가 영영 끝나지 않을 수 있는 경로가 둘 있다

non-daemon의 대가다. `stop(timeout=None)`은 무기한 join이고, 워커가 갇히면 프로세스는 나가지 못한다.

1. **SDK 호출에 타임아웃이 없다** — `open-trading-api/examples_user/kis_auth.py:443-445`가 `requests.get/post`를 `timeout=` 없이 호출한다. 소켓이 멈추면 워커 태스크도, `stop()`의 join도 반환하지 않는다. 신호와 무관하게 성립한다.
2. **워커를 세운 뒤 `try`에 진입하기 전의 창** — 그 사이 인터럽트가 오면 `stop()`이 호출되지 않고, 큐에서 대기 중인 non-daemon 스레드가 인터프리터 종료를 무기한 붙든다(실측 확인).

cron + `flock -n` 환경에서 이 hang은 **조용하다**. 잠금이 계속 점유되어 다음 기동이 실패하고 즉시 종료하며, 거래는 아무 소리 없이 건너뛰어진다.

권고는 둘이다.

- ① **프로세스 실행 시간 상한** — systemd `TimeoutStartSec=`(§8.2) 또는 cron 유지 시 `flock` 안쪽의 `timeout -k 30 3600`. **메인 스레드가 갇히는 경우까지 덮는 유일한 조치다.**
- ② `stop()`에 유한 timeout + 초과 시 `_log`. **단, §5.2의 실측대로 이것은 진단일 뿐 종료 보장이 아니다** — non-daemon인 한 인터프리터 종료에서 다시 막힌다.

### F-2 · `worker.start()`가 `try` 바깥에 있다

F-1의 두 번째 경로를 없애는 한 줄짜리 수정이다. 창이 좁아 발생 확률은 낮지만, 증상(무한 hang + 잠금 점유)이 무겁고 비용이 사실상 0이다.

```python
# vmtrader/broker/kis_broker.py:648
 worker = TaskQueueWorker(on_error=self._log_error)
 self._worker = worker
-worker.start()
-try:
+try:
+    worker.start()
     while self.open_orders:
         ...
 finally:
     worker.stop()
```

### F-3 · SIGINT 경로에서 STALE 기록만 빠진다

§4.3. 거래상 안전은 `reconcile()`이 보장하므로 잃는 것은 감사 추적 한 줄이다. 고치려면 STALE 루프를 `finally` 안, `stop()`·드레인 뒤로 옮긴다. **현행 유지도 방어 가능**하며, 그 경우 운용 문서에 "인터럽트 종료 시 원장은 `SUBMITTED`로 남는다"를 한 줄 적어 두는 편이 낫다.

### F-4 · 트레이딩 평면의 SIGTERM 핸들러는 도입하지 않는 쪽을 권고

§7 표의 첫 행. 넣는다면 핸들러는 **플래그만 세팅**하고 `settle()`의 감시 루프가 회수하도록 한다.

### F-5 · `join_tasks()`의 timeout 분기에 죽은 코드

`deadline = threading.TIMEOUT_MAX if timeout is None else timeout`(`worker.py:105`)에서 `timeout is None`은 바로 위 분기가 이미 반환했으므로 도달하지 않는다. 동작 영향은 없다.

### F-6 · 강제 리밸런싱 경로가 없다

§6.3. `_is_rebalance_day`가 조용히 막으므로, 텔레그램 트리거를 만들기 전에 강제 인자(또는 `rebalance_dates=None` 세션)를 먼저 정의해야 한다. 킬스위치와 `reconcile` halt는 강제의 대상이 아니다.

### F-7 · 상주 전환 시 리셋 지점이 사라진다

§6.2 표. `orders_submitted`와 `trading_halted`는 **프로세스 기동이 유일한 리셋 지점**이다. B안을 검토한다면 이 둘에 사이클 단위의 리셋(또는 명시적 해제 명령)을 먼저 설계해야 한다. A안에서는 문제가 생기지 않는다.

### F-8 · 크래시 자동 재시작은 미체결 주문을 이중으로 낼 수 있다

§8.3. 현재는 cron이 하루 한 번만 기동하므로 발현하지 않는다. **`Restart=on-failure`를 리밸런싱 유닛에 붙이는 순간 새로 생기는 위험**이므로, 자동 재시작을 도입하려면 그 전에 "거래소에서 일하고 있는 미체결 주문"을 사이저가 인지하도록 만들어야 한다.

### F-9 · `task_done()`의 위치가 드레인 배리어의 의미를 정한다

대조군을 다시 읽다가 나온 것으로, **vmtrader의 결함이 아니라 유지해야 할 불변식**이다. smtm은 `task_done()`을 큐에서 꺼내자마자 호출한다 (`smtm/worker.py:62-63`).

```python
task = self.task_queue.get()
self.task_queue.task_done()      # <- runnable 실행 '전'
if task is None:
    ...
runnable(task)
```

처음부터 그랬던 것은 아니다. `4fe407f`("add join queue", 2021-03-01)가 `stop()`에 `task_queue.join()`을 넣을 때는 `task_done()`이 `runnable` **뒤**에 있었고, 그래서 그 조인은 완료 배리어였다. 1년 뒤 `ab54bfa`("stop Worker when runnable make a exception", 2022-05-26)가 예외 처리를 넣으면서 위치를 옮겼다.

```diff
 task = self.task_queue.get()
+self.task_queue.task_done()
 if task is None:
     if self.on_terminated is not None:
         self.on_terminated()
-    self.task_queue.task_done()
     break
-runnable(task)
-self.task_queue.task_done()
+try:
+    runnable(task)
+except Exception:
+    self.logger.error(traceback.format_exc())
+    self.thread = None
+    raise UserWarning("Worker catched exception. force stop!")
```

**예외가 나도 `task_done()`이 빠지지 않게 하려고 위로 끌어올린 것이다.** `finally` 대신 hoisting을 택한 대가로 조인은 "완료 배리어"에서 "**꺼냄 배리어**"로 바뀌었다. 같은 커밋이 통합 테스트에 `time.sleep(0.5)`를 함께 넣은 것이 증거다 — 당시 `operator.stop()`은 상태를 `on_terminated` 콜백 안에서 `"ready"`로 바꿨는데, 옮기기 전에는 `task_done()`이 그 콜백 **뒤**에 있어 조인이 콜백 완료까지 기다렸다. 옮긴 뒤로는 조인이 콜백보다 먼저 반환할 수 있게 되어 `assertEqual(op.state, "ready")`가 흔들렸고, 잠으로 덮었다.

smtm에서 이 변화가 겉으로 드러나지 않은 이유는 **유일한 배리어가 종료 센티넬과 융합되어 있기 때문**이다. 센티넬은 큐의 맨 뒤이고 소비자는 하나이므로, 앞의 태스크가 끝나야 센티넬이 꺼내진다. 배리어를 센티넬 없이 사이클 중간에 부르는 쪽 — 즉 vmtrader의 `join_tasks()` — 에서만 차이가 나타난다. 두 배치를 그대로 재현한 실측(3회 반복 동일):

| 배치 | 중간 배리어 `join()` 반환 시점 | 그 시점의 수집 결과 |
| --- | --- | --- |
| smtm (`get()` 직후) | **0.00초** | `[]` — 태스크가 아직 실행 중 |
| vmtrader (`finally`) | 0.30초 | `['fill']` |

smtm의 배치를 그대로 가져왔다면 메인 스레드가 **아직 수집되지 않은 체결을 기표**했을 것이다. ADR-0008의 회계 단일 작성자 규율은 `task_done()`이 `finally`에 있어야만 성립한다 — `worker.py`의 그 두 줄은 취향이 아니라 요구사항이다.

조치는 없다(설계대로). 남길 것은 **불변식 한 줄**이다. `task_done()`을 `runnable` 앞으로 옮기는 어떤 리팩터링도 `join_tasks()`의 의미를 조용히 무효로 만든다. 현재는 `test_join_tasks_reports_whether_the_queue_drained`가 이를 고정한다 — 배치를 옮기면 그 테스트가 깨진다.

> smtm이 주는 교훈은 배치 자체보다 **드러나는 방식**에 있다. 배리어를 건드린 변경은 그 자리에서 티가 나지 않았고, 몇 년 뒤 전혀 다른 계약(종료 콜백의 완료 시점)에서 잠 한 줄로 덮였다.

## 10. 결론과 조치

**non-daemon은 옳은 선택이다.** smtm의 `daemon=True`는 상주 프로세스가 워커에게 종료를 인질로 잡히지 않기 위한 것이고, vmtrader의 `daemon=False`는 사이클보다 오래 사는 스레드가 없다는 전제 위에서 체결 유실 0과 회계 단일 작성자 배리어를 얻기 위한 것이다. 전제가 다르므로 결론이 달라야 정상이며, **사이클이 10~20분이 되어도 전제는 그대로다.**

**신호 핸들러의 부재도 옳다.** 단 그것은 "신호를 받아도 안전하기 때문"이지 "신호가 오지 않기 때문"이 아니다. 남는 실질 위험은 신호가 아니라 **타임아웃 없는 SDK 호출 + 무기한 join**이며, 이는 잠금 점유라는 조용한 실패로 나타난다.

**텔레그램 강제 리밸런싱은 A안(방아쇠만)으로 흡수한다.** 그러면 위 두 결론이 모두 유지된다. B안은 daemon 논쟁 하나가 아니라 §6.2의 전제 여섯 개를 동시에 여는 일이다.

| 우선순위 | 조치 | 대상 | 비용 |
| --- | --- | --- | --- |
| 1 | 프로세스 실행 시간 상한 — `timeout -k 30 3600` (cron 유지 시) 또는 `TimeoutStartSec=` (systemd timer) | cron 두 줄 / 유닛 파일 | 한 줄 |

## 11. 워커는 파이프라인의 어느 단계에 놓이는가

§2가 두 워커의 **구조**를 비교했다면, 여기서는 주문 한 건이 목표 비중에서 포트폴리오 기표까지 가는 길을 단계로 끊고 **워커가 어느 칸에 놓이는지**를 본다. 새 단계를 워커에 넘길지 판단할 때 쓸 기준을 세우는 것이 목적이다.

### 11.1 일곱 단계와 실행 스레드

| # | 단계 | 하는 일 | 실행 스레드 | 코드 |
| --- | --- | --- | --- | --- |
| 1 | 목표 산출 | 스냅샷 하나로 전 종목 수량 결정 | 메인 | `pcm.py` → `order_sizer` |
| 2 | 안전 점검 | 킬스위치·주문 한도·장중 여부·수량 클램프 | 메인 | `kis_broker.py:459-505` |
| 3 | 제출 | `place_market_order` — 버스트로 쏜다 | 메인 | `:516` |
| 4 | 접수 기록 | `record_intent` → `record_submitted` → `open_orders` 등록 | 메인 | `:513`, `:527-535` |
| 5 | 체결 조회 | `get_order_report` — 주문당 1회 왕복 | **워커**(settle) / 메인(update) | `:560`, `:734` |
| 6 | 증분화·버퍼링 | 누적→증분 환산, 원장 기록, `_fill_buffer` 적재 | **워커** | `:561-587` |
| 7 | 기표·마감 | `transact_asset`, `FILLED`/`STALE` 전이 | 메인 (배리어 이후) | `:593-618`, `:753` |

경계가 하나 더 있다. **다음 기동의 대조**(`reconcile.py:70`)는 프로세스가 죽은 뒤의 진실을 맞추는 단계이므로 스레드 논의 밖이며, 이 단계가 있기 때문에 5~7이 실패해도 거래상 안전이 유지된다.

**워커가 쓰이는 것은 5·6 두 단계뿐이다.**

### 11.2 나머지 단계를 워커에 줄 수 없는 이유

**1·2단계** — 한 번만 일어나고, 결과가 사이클 전체의 진행 여부를 바꾼다. `check_order`의 `KillSwitchEngaged`는 `submit_order` 밖으로 다시 던져져 사이클을 세운다(`:504-505`). 워커의 `on_error`는 "이 태스크만 버리고 다음으로"라는 뜻이므로, **중단시켜야 할 예외를 삼키는 자리**가 된다.

**3단계** — 두 가지가 동시에 걸린다.

- **ADR-0006(버스트 제출)** — 모든 주문이 같은 스냅샷에서 나왔으므로 시장 도달 시각이 몰려 있어야 한다. 5단계와 큐를 공유하면 제출이 폴 뒤에 줄을 서고, 마지막 종목이 첫 종목보다 몇 분 늦게 나간다. smtm의 `base_exchange_trader`가 정확히 그 구조다(주문 전송과 결과 조회가 한 큐).
- **비멱등성** — 주문 엔드포인트는 재시도가 곧 이중 포지션이다(`:519-521`). 워커의 관용적 실패 처리와 상극이다.

**4단계** — 워커가 놓이는 자리가 아니라 **워커 때문에 생긴 비용**을 지는 자리다. 원장은 SQLite라 연결이 스레드를 넘지 못하고, 5·6단계를 워커에 준 대가로 `ledger_factory`가 존재해 태스크마다 연결을 새로 연다(`:743-750`). 워커 도입 비용을 셀 때 빠뜨리기 쉬운 항목이다 — **스레드를 하나 만들면 그 아래 계층의 자원 모델이 따라온다.**

**7단계** — 포트폴리오는 락이 없고 타임스탬프 단조성에 민감하다. 기표는 반드시 단일 작성자여야 하므로 배리어 뒤로 되돌아온다(ADR-0008).

### 11.3 같은 코드가 한 곳에선 워커, 한 곳에선 인라인

가장 선명한 증거는 `update()`다. **5·6·7단계를 그대로, 워커 없이** 돌린다(`:806-813`).

```python
for order_no in list(self.open_orders):
    if self._poll_once(order_no, self.ledger):
        done.append(order_no)
self._drain_fill_buffer()
```

반복성도 I/O 지배성도 `settle()`과 같은데 워커가 없다. 다른 것은 **그동안 메인 스레드가 감시할 것이 있는가** 하나뿐이다. `settle()`은 킬스위치와 마감 시각을 계속 봐야 하고(`:666-671`), `update()`는 사이클 사이에 한 번 훑고 끝난다.

> 워커의 존재 이유는 "빨리 하려고"가 아니라 **"기다리는 동안 메인 스레드가 다른 것을 봐야 해서"**다. 병렬성이 목적이었다면 워커는 하나가 아니라 여럿이었을 것이다.

### 11.4 배리어가 지키는 것은 체결 버퍼만이 아니다

`_poll_once`는 워커 스레드에서 **공유 상태를 락 없이 고친다.**

```python
state['booked_quantity'] = report.filled_quantity     # :586  open_orders 안의 dict
task['done'].append(task['order_no'])                 # :747  메인 스레드가 읽을 리스트
```

안전한 이유는 하나뿐이다 — 그 시간 동안 메인 스레드가 `join_tasks()`에 서 있기 때문이다. 즉 배리어는 락으로 보호되는 `_fill_buffer`를 위한 것이 아니라 **락이 없는 나머지 전부**를 위한 것이다.

여기서 따라오는 규칙이 있다. `join_tasks()`가 시간 안에 끝나지 않았다고 해서 **라운드를 포기하고 진행해서는 안 된다.** 그러면 6단계와 7단계가 같은 dict를 동시에 만진다. 드레인 타임아웃을 도입한다면 그것은 진단(로그)이어야 하고, 배리어 자체는 끝까지 강제해야 한다.

### 11.5 판정 규칙

새 단계를 워커에 넘길지는 **네 조건이 모두 참일 때만** 그렇다.

| 조건 | 물음 |
| --- | --- |
| 반복성 | 같은 모양의 일이 개수가 변하는 만큼 반복되나 |
| I/O 지배 | 그 시간의 대부분이 대기인가 (CPU라면 GIL 때문에 이득이 없다) |
| 값으로 환원 | 결과를 자료구조 하나에 담아 돌려줄 수 있나 — 또는 배리어 안에서만 상태를 만지나 |
| 감시 필요 | 기다리는 동안 메인 스레드가 봐야 할 것이 있나 |

넘기지 **말아야** 할 신호는 이쪽이다.

| 신호 | 이유 | 해당 단계 |
| --- | --- | --- |
| 예외가 사이클 전체를 세워야 한다 | `on_error`는 "버리고 계속"이다 | 1·2 |
| 시각이 몰려 있어야 한다 | 큐는 순서를 지키지만 시각을 지키지 않는다 | 3 |
| 재시도가 위험하다 (비멱등) | 관용적 실패 처리와 상극 | 3 |
| 단일 작성자 불변식을 만진다 | 배리어 뒤로 미뤄야 한다 | 7 |
| 한 번만 일어난다 | 스레드 비용만 남는다 | 1·4, `update()` |

**요약.** 이 워커는 7단계 중 5·6, 그것도 `settle()` 안에서만 산다. smtm처럼 컴포넌트마다 상주시키지 않는 이유는 성능이 아니라 규율이다 — 워커가 존재하는 구간을 배리어로 앞뒤가 막힌 두 단계로 좁혀 두었기 때문에 락 없는 자료구조를 그 안에서 안전하게 쓸 수 있고, 7단계의 단일 작성자 규율이 성립한다. 워커를 다른 단계로 넓히자는 제안이 오면 실제로 검토할 것은 스레드가 아니라 **그 배리어가 어디로 옮겨가는가**다.

## 12. 왜 이만큼을 기록하는가 — 단일 파일 스크립트와의 대조

같은 일(월 1회 비중 리밸런싱)을 파일 하나로 끝내는 구성이 있다. 국내 퀀트 예제 코드에서 흔히 보이는 형태이며, 여기서 대조군으로 삼는 것은 **특정 구현이 아니라 그 구성 방식**이다. 이 절의 목적은 "우리 쪽이 왜 이렇게 큰가"가 아니라 **"우리가 기록하는 것들은 무엇을 대신하고 있는가"**를 묻는 것이다.

### 12.1 대조군의 구성

클래스도 함수도 거의 없이 위에서 아래로 흐른다. 계좌 조회 → 지표로 목표 비중 산출 → 목표와 현재 비중의 차이만큼 매매 수량 계산 → 매도 → 짧은 `sleep` → 매수 → 이번 주기를 실행했다는 표식을 파일에 기록. cron이 하루 한 번 실행하고 프로세스는 끝난다.

**프로세스 모델은 vmtrader와 같다**(단발). 다른 것은 그 안에서 무엇을 하느냐다.

### 12.2 단순함의 정체 — 7단계 중 넷만 있다

| §11 단계 | 단일 파일 구성 | vmtrader |
| --- | --- | --- |
| 1 목표 산출 | 지표로 비중을 가감 | 사이저 |
| 2 안전 점검 | 실행 여부 플래그, 투자 비중 상수 | 킬스위치·주문 한도·장중·클램프 |
| 3 제출 | 시장가 매도 → `sleep` → 시장가 매수 | 동일 (버스트) |
| 4 접수 기록 | **없음** — 주문 응답을 출력하고 버린다 | 원장 `INTENT` → `SUBMITTED` |
| 5 체결 조회 | **없음** | 워커 |
| 6 증분화·버퍼링 | **없음** | 워커 |
| 7 기표·마감 | **없음** | 배리어 뒤 메인 스레드 |

**워커가 없는 이유는 워커를 안 쓰기로 해서가 아니라 5·6단계가 존재하지 않기 때문이다.** 주문을 내고 나면 그 주문이 어떻게 됐는지 이 프로세스는 영영 묻지 않는다. 다음 실행이 계좌를 새로 읽고, 거기 찍힌 결과가 곧 진실이다.

같은 이유로 포트폴리오 객체가 없다. 회계 상태를 프로세스가 들고 있지 않으므로 **단일 작성자 규율도, 타임스탬프 단조성도, 배리어도 필요하지 않다.** ADR-0008이 지키려는 불변식 자체가 없는 것이다.

### 12.3 프로세스 밖으로 살아남는 것

두 구성이 다음 기동에 남기는 것을 나란히 놓으면 차이가 한눈에 보인다.

| 남기는 것 | 단일 파일 구성 | vmtrader |
| --- | --- | --- |
| 형태 | 작은 JSON 파일 하나 | SQLite 원장 |
| 내용 | "이번 주기를 실행했다"는 표식 (연월 문자열 정도) | 주문별 `INTENT`/`SUBMITTED`/`FILLED`/`REJECTED`/`STALE` + 체결 기록 |
| 쓰는 시점 | 매수까지 **전부 끝난 뒤 한 번** | 거래소를 부르기 **전에** 의도부터 |
| 무엇에 답하나 | "이번 주기에 리밸런싱했는가" | "이 주문이 나갔는가, 얼마가 체결됐는가, 왜 끝났는가" |
| 중복 방지 | 주기 표식 하나 | `(주문번호, 누적체결수량)` 키 |

이런 구성에서 파일에 쓰는 지점은 대개 코드 전체에 **한 곳뿐**이다. 프로세스가 남기는 사실이 표식 하나라는 뜻이고, 그것이 이 형태가 단순한 진짜 이유다.

### 12.4 그 차이가 만드는 실패 모드

셋 다 이 저장소의 소견과 정확히 맞물린다.

1. **매도와 매수 사이의 크래시** — 그 사이에서 프로세스가 죽으면 실행 표식은 아직 쓰이지 않았으므로, 다음 실행이 "아직 안 했다"고 판단해 **리밸런싱 전체를 다시 시작한다.** 이미 팔린 것은 계좌에 반영되어 있으니 매도는 재현되지 않지만, 매수는 처음부터 다시 계산되어 나간다. 이것이 F-8이 경고한 "자동 재시작이 미체결 주문을 이중으로 낼 수 있다"의 원형이며, vmtrader가 **거래소를 부르기 전에** 의도를 원장에 쓰는(`kis_broker.py:513`) 이유다.

2. **주문 호출의 예외** — 주문 루프에 예외 처리가 없는 경우가 많다. 종목 하나에서 예외가 나면 뒤의 종목은 주문되지 않고, 그 사실이 어디에도 남지 않는다. vmtrader는 같은 자리에서 `REJECTED`를 기록하고 **재시도하지 않는다**(`kis_broker.py:519-521`) — 주문 엔드포인트가 비멱등이기 때문이며, 그 판단을 코드가 아니라 원장이 증명한다.

3. **표식 쓰기의 실패** — 매매는 끝났는데 파일 쓰기가 실패하면 다음 실행이 다시 리밸런싱한다. 읽기 쪽에서 예외를 통째로 삼키는 구성이라면 파일이 깨져도 "첫 실행"으로 보인다.

### 12.5 결론 — 복잡도의 출처

세 층으로 정리된다.

| 층 | 단일 파일 구성 | vmtrader | 대가 |
| --- | --- | --- | --- |
| 진실의 소재 | 거래소 계좌 (매번 새로 읽음) | 프로세스 안의 포트폴리오 + 원장 | 단일 작성자 규율이 필요해진다 |
| 주문의 사후 | 보지 않음 | 예산 안에서 폴링 | 5·6단계와 **워커**가 생긴다 |
| 기록의 시점 | 전부 끝난 뒤 | 거래소를 부르기 전 | 중간 크래시가 증거를 남긴다 |

**이 보고서가 다룬 것들 — non-daemon, 스레드 join, 드레인 배리어, `task_done`의 위치, 종료 훅 — 은 전부 두 번째 줄에서 파생된다.** "주문을 낸 뒤 그 결과를 이 프로세스가 책임지고 확인한다"는 결정 하나가 워커를 부르고, 워커가 배리어를 부르고, 배리어가 종료 규율을 부른다.

역으로 읽으면 이렇게도 말할 수 있다. 매매 후 확인을 포기하고 거래소를 유일한 진실로 삼으면 §5부터 §11까지의 논의는 **한 줄도 필요 없다.** 그 단순함은 공짜가 아니라 **부분 체결과 미체결을 그 사이클 안에서 알 수 없다는 것**과 맞바꾼 것이다. 어느 쪽이 옳은지는 전략이 정한다 — 주기적 시장가 리밸런싱이라면 앞쪽이 합리적이고, 체결을 사이클 안에서 기표해야 하는 설계라면 뒤쪽 외에 선택지가 없다.
