# ADR-0009: `LiveTradingSession`은 상주 프로세스가 아니라 cron 단발 실행이다

| 항목 | 내용 |
| --- | --- |
| 상태 | **제안됨 (Proposed)** — 미구현. [ADR-0006](0006-decouple-submit-from-fill.md)·[ADR-0008](0008-task-queue-fill-pump.md)을 **보강**한다 (대체 아님) |
| 작성일 | 2026-08-19 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §2.4, §10.2-b, §11 Q10 |
| 관련 요구 | FR-7·FR-17·FR-21·FR-23, NFR-9, C-15 ([spec/kis-broker.md](../spec/kis-broker.md)) |

## 맥락

라이브 세션의 프로세스 모델이 미정이었다(설계 Q10). 후보는 둘 — 벽시계 대기 루프를 도는 **상주 데몬**과, cron이 이벤트 시각마다 프로세스를 새로 띄우는 **단발 실행**이다.

운용 호스트를 실측했다 (2026-08-19, `ssh stock-bot`). 공유 t3.micro(RAM 904MiB, 가용 약 260~590MiB 변동, 루트 8GB 중 가용 0.7GB — C-15)이고, 동거 KIS 봇 전원(hybridma 실전 다계좌·autobotex 등)이 **`cron + flock` 단발 패턴**(`cron_run.sh --workdir --venv --entry --log`, TZ=Asia/Seoul)으로 돌며, **상주 트레이딩 프로세스는 하나도 없다**(ps 실측).

한편 설계는 이미 단발에 필요한 부품을 전부 갖추고 있다: FR-7(기동 시 잔고 기반 재구성), FR-16(원장 영속), §10.2-b(자본곡선은 장 마감 1회), ADR-0008(워커는 사이클 수명·상주 금지). 라이브의 하루 이벤트는 **리밸런싱 1회와 장 마감 기록 1회, 둘뿐**이다.

## 결정

**`LiveTradingSession`은 cron 단발이다. 기동 1회 = 사이클 1회이며, 하루 2종의 기동으로 구성된다.**

| 기동 | cron 시각 (기본) | 동작 |
| --- | --- | --- |
| **A. 리밸런싱** | 10:00 KST 평일 (FR-21, 설정값) | reconcile(F7~F10) → 휴장·리밸런싱 날 여부 판정(FR-9, `Rebalance` 스케줄 — 아니면 즉시 종료) → 사이클 1회(접수→정산, FR-23 시간 예산) → 종료 |
| **B. 장 마감(EOD)** | 15:30 이후 평일 | STALE 잔량 1회 흡수(설계 §10.6.4) → 시가평가 → **자본곡선 1회를 영속 저장에 기록**(§10.2-b) → 잔고 대조 → 종료 |

- **flock 잠금**: 호스트 관례를 따른다. 기동 A·B는 **같은 잠금 파일**을 공유해 겹침 실행을 배제한다.
- 기동 간 상태 전달은 **원장(SQLite)과 브로커 잔고뿐**이다(FR-7·FR-16). 인메모리 상태는 프로세스와 함께 죽는 것이 정상이다.
- 분 단위 슬롯 선정·동거 봇 슬롯 회피는 스펙이 아니라 **운용 사안** — Phase 3 운용 가이드(`docs/user/`)에 기록한다.

## 검토한 대안

| 대안 | 내용 | 기각 사유 |
| --- | --- | --- |
| 1. 상주 데몬 (systemd 등) | 벽시계 대기 루프로 다음 이벤트까지 sleep | 하루 2개 이벤트 사이 약 5시간을 pandas 로드 상태로 점유 — 가용 260~590MiB 호스트에서 정당화 불가(NFR-9). 호스트에 상주 전례 0(ps 실측). 장기 실행의 토큰 만료(C-2)·크래시는 어차피 FR-7 경로로 처리해야 해 상주의 이득이 없다 |
| 2. 단일 기동이 10:00~15:30 생존 | 리밸런싱 기동이 마감까지 살아 자본곡선까지 기록 | 점유 시간 동일 + 크래시 시 자본곡선 유실. FR-23이 사이클을 60분으로 절단하는데 프로세스만 5시간 사는 비대칭 |
| 3. 자본곡선을 리밸런싱 종료 시점에 기록 | 기동 1회로 축소 | §10.2-b에서 이미 기각 — 백테스트의 `market_close` 기록(`backtest.py:437-442`)과 다른 시계열이 되어 통계 의미가 갈라진다 |

## 근거

1. **호스트 관례 실측** (C-15): 동거 봇 전원이 cron+flock 단발이다. 같은 패턴이면 운용자(동일인)의 감시·로그·잠금 관리가 하나의 방식으로 통일된다.
2. **FR-7이 단발을 공짜로 만든다**: 매 기동이 재기동이므로 복구 경로(A-4)가 곧 정상 기동 경로다 — 복구 코드가 매일 실행되어 죽은 코드가 되지 않는다.
3. **ADR-0008과 자연 정합**: "세션 프로세스에 리밸런싱 사이클보다 오래 사는 스레드가 없다"(§10.6.2)의 완성형이 "프로세스 수명 = 사이클 수명"이다. 워커·버퍼·원장 연결 어느 것도 프로세스 경계를 넘도록 설계되지 않았다.
4. **자원** (NFR-9): 단발은 피크 점유가 기동 시간(분 단위)에 국한되고, 버스터블 인스턴스의 CPU 크레딧·메모리를 동거 실계좌 봇과 시분할한다.

## 결과

- `trading/live.py`는 대기 루프가 아니라 **단발 엔트리**다 (설계 §3.2). `SimulationEngine`의 라이브 대체물(이벤트 대기 루프)은 만들지 않는다 — 이벤트 사이의 대기는 cron이 한다 (§2.4).
- **자본곡선 시계열의 영속화가 새로 필요하다** — 백테스트는 인메모리 리스트로 충분했지만 라이브는 기동이 매번 죽는다. 원장 DB에 append한다 (§10.2-b).
- 기동 A가 크래시해도 기동 B는 독립적으로 돌아 기록·대조가 수행된다 — 자연스러운 일일 감시 지점이 생긴다.
- `Rebalance` 스케줄의 "오늘이 리밸런싱 날인가" 판정이 기동 A 초입에 필요하다 — cron은 매 평일 기동하고 판정은 프로세스가 한다(휴장일 판정 FR-9와 같은 위치).
- 동거 봇과의 KIS 레이트리밋 간섭 여부는 **미확인**이다(부과 단위가 앱키/계좌/IP 중 무엇인지 — 스펙 §8). 기본 10:00 기동은 동거 봇의 주문 집행 슬롯(14:30~15:20 대역)과 겹치지 않으나 조회 전용 잡과 인접하므로 Phase 3 스모크에서 확인한다.
