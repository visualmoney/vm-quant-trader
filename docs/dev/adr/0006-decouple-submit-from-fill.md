# ADR-0006: 주문 접수와 체결 반영을 분리한다

| 항목 | 내용 |
| --- | --- |
| 상태 | **제안됨 (Proposed)** — 미구현. [ADR-0002](0002-blocking-fill-polling.md)를 **대체** |
| 작성일 | 2026-08-19 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §10.1~10.4 |
| 관련 요구 | FR-3·FR-19·FR-23, NFR-7 ([spec/kis-broker.md](../spec/kis-broker.md)) |

## 맥락

ADR-0002는 `submit_order()`가 접수 후 체결까지 동기 폴링하도록 정했다. 그 근거는 "주문 1건의 생애가 한 함수에서 끝나 원장 전이를 한곳에 둘 수 있다"였고, 대안(접수/체결 분리)은 *"호출 형태가 어차피 같다"*는 이유로 기각했다.

이 기각 논리는 **틀렸다.**

qstrader는 스케줄 구동 엔진이다. 사이저는 리밸런싱 시점의 스냅샷 하나로 목표 수량 **전건을 한꺼번에** 산출한다(`portcon/order_sizer/long_short.py:64-114`가 equity와 포지션을 읽는 지점은 리밸런싱당 각 1회다). 백테스트는 그렇게 산출된 주문들을 **같은 순간에** 체결시킨다(`broker/simulated_broker.py:672-682`).

블로킹 폴링은 이 주문들을 **직렬화**한다. 20종목이면 20번째 주문이 첫 주문보다 수십 분 늦게 시장에 닿는다. 그 사이 시장은 움직이고, 20번째 주문은 이미 낡은 스냅샷으로 산출된 수량을 낡은 가격 가정 위에서 집행한다. **블로킹은 백테스트의 원자성을 보존하는 것이 아니라 훼손한다.**

## 결정

**`submit_order()`는 접수만 하고 즉시 반환한다.** 체결은 두 경로로 수집한다.

| 단계 | 동작 |
| --- | --- |
| **접수** | 가드 → 원장 INTENT → `order_cash` → 원장 SUBMITTED → **미결 집합에 추가하고 반환**. 블로킹 없음 |
| **정산(settle)** | 리밸런싱 종료 후, **시간 예산 안에서** 미결 집합을 폴링해 체결분을 `Portfolio`에 반영 |
| **후속** | 예산 초과분은 원장 STALE. 이후 `update(dt)`가 재조회해 늦은 체결을 흡수 |

`Broker` ABC docstring이 기술한 *"It contains a queue of open orders"*(`broker/broker.py:20-21`) 모델로 **돌아온다**.

## 검토한 대안

| 대안 | 내용 | 기각 사유 |
| --- | --- | --- |
| A. 블로킹 (ADR-0002) | `submit_order`가 체결까지 대기 | 주문 직렬화로 스냅샷 충실도 저하. 대기 중 킬스위치·장마감에 반응 불가 |
| B. smtm식 워커 루프 + 콜백 | 별도 스레드·큐·콜백 계약 | 코어 침습이 크다. `Broker` ABC 밖에 두 번째 제어 흐름이 생겨 백테스트와 라이브의 코드경로가 갈라진다 — 이 연동의 목적에 반한다 |

## 근거

**대조군의 실증.** `smtm`은 가동 중인 라이브 매매 시스템이며 같은 분리를 택했다.

| 요소 | 위치 |
| --- | --- |
| 거래 루프가 체결을 기다리지 않는다 | `smtm/trading_operator.py:127-138` |
| 체결은 콜백으로 나중에 도착한다 | `smtm/trader/trader.py:16`, `:40` (`state: requested → done`) |
| 미결 주문을 별도 집합에 보관하고 별도 타이머가 순회한다 | `smtm/trader/upbit_trader.py:227`, `:236-281` |
| 미결이 남아 있는 동안만 폴링을 재무장한다 | `smtm/trader/base_exchange_trader.py:24,110-111` |
| 시뮬레이션은 같은 계약에서 콜백을 즉시 호출한다 | `smtm/trader/simulation_trader.py:48-50` |

**맥락 차이**: smtm은 24시간 시장이라 하드 데드라인이 없다. KRX는 15:30에 닫힌다 — 그래서 우리는 smtm에 없는 **시간 예산**이 필요하다 (FR-23).

## 결과

- **리밸런싱에 정산 단계가 생긴다.** `LiveTradingSession`이 `qts(dt)` 이후 `broker.settle(deadline)`을 호출한다. 백테스트 세션에는 이 단계가 없다.
- **`update(dt)`의 책임이 늘어난다** — 시가평가·대조에 더해 미결 주문 수집. [ADR-0004](0004-promote-update-to-abc.md)의 승격이 더 중요해진다.
- **부분체결이 시간에 걸쳐 여러 번 반영된다.** 같은 주문에서 체결량이 증가할 때마다 증분만큼 `Transaction`을 만든다 — 원장의 UNIQUE 제약이 이중 반영을 막는다 (NFR-6).
- **체결 확인 순서가 역전될 수 있다.** 이것이 [ADR-0007](0007-engine-clock-timestamps.md)을 강제한다.
- ADR-0002가 내세운 이점(주문 생애가 한 함수)은 잃는다. 원장 전이가 접수 경로와 정산 경로에 나뉘므로, **상태기계를 원장 모듈에 명시적으로 두어야** 한다.
- (2026-08-19 추기) 대안 B의 기각은 유지되나, 그 부품인 **단일 FIFO 워커 큐**(`smtm/worker.py`)는 [ADR-0008](0008-task-queue-fill-pump.md)이 정산 단계의 실행 기반으로 **제한 채택**한다 — 콜백 계약·상주 스레드 없이. 본 결정(접수/체결 분리)은 바뀌지 않는다.
