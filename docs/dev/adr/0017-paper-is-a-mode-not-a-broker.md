# ADR-0017: 모의투자는 브로커가 아니라 모드다

| 항목 | 내용 |
| --- | --- |
| 상태 | **채택됨** (2026-08-23) |
| 성격 | 기능 추가 + 원장 스키마 변경 (하위호환 마이그레이션 포함) |
| 관련 | [ADR-0013](0013-real-money-promotion-criteria.md), [ADR-0015](0015-venue-neutral-live-package.md), [보고서 20260823-01 §5](../reports/20260823-01-codebase-comprehension-strategy.md) |

## 맥락

두 가지 질문이 함께 제기되었다. **`broker/paper_broker.py`가 필요한가**, 그리고 **모의투자 계좌에 붙어 ETF를 매매하는 것이 라이브/페이퍼 모드 전환으로 이루어지는가.**

조사 결과 세 가지가 확인되었다.

**1. ETF 매매에는 아무것도 필요 없다.** KIS의 ETF/ETN API 그룹은 6개 전부 시세·NAV 조회이며 **주문 엔드포인트가 없다.** ETF 주문은 국내주식 주문 API를 그대로 쓴다. DB증권도 같아서 `kr_stock_order` 하나가 주식과 ETF를 모두 받는다. 즉 `BrokerClient.place_market_order('EQ:069500', qty)`는 이미 ETF 주문이며, 유니버스에 심볼을 넣는 것 외에 할 일이 없다.

**2. 모의투자 연결도 이미 된다.** `KisGateway.connect(svr='vps')`가 모의 서버로 붙고, 그것이 기본값이다. 실전은 `svr='prod'`를 코드에 직접 써야만 닿는다.

**3. 그런데 엔진은 자기가 어느 쪽인지 모른다.** 그리고 이것이 실제 구멍을 만든다. `scripts/promotion_check.py`는 자기 docstring에 *"reads the ledger a paper deployment produced"*라고 쓰지만, 원장에 그것을 확인할 수단이 없다. 스키마는 `orders` / `fills` / `equity_curve` 세 테이블뿐이고 어디에도 venue·mode·account가 없다. **실전 원장을 넣어도, 두 계좌가 섞인 원장을 넣어도 똑같은 PASS가 나온다.** 실전 승격은 이 프로젝트에서 유일하게 되돌릴 수 없는 행위인데(ADR-0013), 그 판정의 입력이 검증되지 않고 있었다.

## 결정

### 1. `PaperBroker`를 만들지 않는다

증권사의 모의투자는 시뮬레이터가 아니라 **실제 venue**다. 주문 접수, 부분 체결, 거절, rate limit이 전부 실전과 같은 엔드포인트에서 같은 모양으로 일어난다. **모의가 실전과 동일한 코드 경로를 탄다는 것이 리허설의 유일한 가치**이며, ADR-0013의 승격 기준 7항은 전부 그 전제 위에 있다. 클래스를 가르면 모의에서 통과한 코드가 실전에서 도는 코드와 달라지고, 승격 판정이 아무것도 증명하지 못하게 된다.

`LiveBroker` 하나를 유지한다. 증권사도, 모의/실전도, 게이트웨이가 정한다.

> 참고로 "페이퍼 트레이딩"이 **실시간 시세에 대고 로컬에서 가상 체결**하는 것을 뜻한다면 그것은 별개의 물건이고, 역시 새 클래스를 필요로 하지 않는다 — `SimulatedBroker`에 `LiveDataHandler`를 물리면 된다. 다만 `BacktestTradingSession`이 브로커와 거래소를 하드코딩하고 있어(보고서 §9-2, 권고 R8) 지금은 조립이 막혀 있다.

### 2. 대신 모드를 1급 개념으로 올린다

| 계층 | 변경 |
| --- | --- |
| `BrokerClient` Protocol | `venue: str`, `mode: str` 속성 추가. 엔진은 모의와 실전을 **구별할 수 없으므로**(같은 엔드포인트가 같은 모양으로 답한다) 서버를 고른 게이트웨이가 선언한다 |
| `KisGateway` | `venue = 'kis'`, `mode = 'paper' if env_dv == 'demo' else 'real'`. 별도 인자가 아니라 **인증에 쓴 서버에서 파생**시켜, 실제로 접속한 계좌와 어긋날 수 없게 한다 |
| `LiveBroker` | 생성 시 클라이언트에서 읽어 로그 접두어와 원장 스탬프에 쓴다. 명시 인자가 우선하므로 테스트 더미는 둘 다 없어도 된다 |
| `OrderLedger` | `meta` 테이블 신설 + `equity_curve.mode` 컬럼. `stamp_identity()`가 **다른 배포가 열면 `LedgerIdentityConflict`를 던진다** |
| `promotion_check.py` | 첫 번째 기준으로 `ledger-is-paper` 추가 |

**핵심은 검출이 아니라 예방이다.** 원장은 자기를 만든 배포(venue·mode·account)를 기억하고, 다른 배포가 스탬프를 찍으려 하면 거부한다. 실수가 아직 싼 유일한 순간이 그때다 — 두 배포가 한 파일에 쓰기 시작하면 양쪽 다 유효한 행을 남기므로 사후에 조용히 섞인다.

행 단위 `mode`도 함께 둔다. 스탬프가 막지 못하는 경우 — 신원이 기록되기 이전의 원장, 손으로 조립한 파일 — 를 감사할 수 있어야 하기 때문이다. 기본값은 `'paper'`가 아니라 **`'unknown'`**이다. 관대한 기본값을 두면 기존 원장 전부가 이 기준을 공짜로 통과하는데, 그것이 바로 이 결정이 대체하려는 신뢰다.

### 3. ETF 증권거래세 면제를 표현 가능하게 한다

국내 상장 ETF는 증권거래세법상 과세대상 '주권'이 아니라 수익증권이므로 **매도 시 증권거래세가 없다.** 그런데 `KoreaStockFeeModel`은 `quantity` 부호만 보고 세금을 물렸고, `examples/sixty_forty_kr.py`는 KODEX 200·KOSEF 두 ETF에 `tax_pct=0.0018`을 적용하고 있었다. ETF만으로 구성된 포트폴리오에서 이것은 세율을 조금 틀린 것이 아니라 **내지 않는 세금 전액을 부과**한 것이고, 월간 리밸런싱이면 매달 걷힌다.

엔진은 여섯 자리 코드만 보고 ETF와 개별주를 구별할 수 없다. 따라서 조립부가 알려 준다:

```python
KoreaStockFeeModel(
    commission_pct=0.00015,
    tax_pct=0.0018,                                  # 개별주에 유효
    tax_exempt_assets={'EQ:069500', 'EQ:148070'},    # ETF는 면제
)
```

세율을 0으로 낮추는 대신 면제 집합을 두는 이유는, 그래야 **ETF와 개별주를 섞은 유니버스**가 하나의 모델로 표현되기 때문이다. 기본값은 빈 집합이라 기존 동작이 보존된다.

> 세율 자체는 법정 형태이지 특정 증권사의 수수료표가 아니다. 실제 값은 거래하는 증권사 기준으로 확인할 것.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| **`PaperBroker` 별도 클래스** | 위 §1. 모의가 실전과 같은 경로를 타는 것이 리허설의 전부다 |
| **현행 유지 — 게이트웨이 인자만** | 코드 변경은 0이지만 `promotion_check`가 계속 입력을 검증하지 못한다. 승격이 되돌릴 수 없는 행위라는 점이 이 비용을 감당 불가로 만든다 |
| **`mode`를 `LiveBroker` 생성자 인자로** | 게이트웨이가 접속한 서버와 어긋날 수 있다. 조립부에 `svr='prod'`, `mode='paper'`를 나란히 쓰는 순간 원장이 거짓말을 시작한다. 파생시키면 그 상태가 표현 불가능해진다 |
| **원장 혼입을 사후 검출만** (스탬프 없이 행 mode만) | 검출되는 시점에는 이미 증거가 오염되어 있다. 예방이 가능한데 검출로 만족할 이유가 없다 |
| **`mode` 기본값을 `'paper'`로** | 안전해 보이지만 반대다. 아무것도 기록하지 않은 원장이 자동으로 리허설로 인정된다 |
| **ETF용 `KoreaEtfFeeModel` 신설** | ETF와 개별주를 섞은 유니버스를 표현할 수 없다. 자산별 속성을 모델 종류로 나누면 조합마다 모델이 필요해진다 |

## 결과

**좋은 점**

- 승격 판정이 **자기 입력을 검증한다.** `ledger-is-paper`가 첫 기준이며, 실패하면 나머지 측정은 의미가 없다는 것이 순서로 표현된다.
- 모의와 실전이 한 파일에 섞이는 사고가 **구조적으로 불가능**해진다.
- ETF 전략의 비용 모델이 실제 세제와 일치한다.
- `PaperBroker`가 없으므로 모의에서 검증한 코드가 실전에서 도는 코드와 **글자 그대로 같다.**

**나쁜 점 / 비용**

- **기존 원장은 `ledger-is-paper`를 통과하지 못한다.** 신원을 기록한 적이 없으므로 `'unknown'`이고, 이것은 의도된 것이다. 승격을 앞둔 배포라면 새 원장으로 재시작하거나, `meta`에 신원을 손으로 넣고 그 사실을 남겨야 한다.
- 원장 스키마가 바뀐다. `equity_curve`에 컬럼이 추가되므로 기존 파일에 `ALTER TABLE` 마이그레이션이 필요하고, 이는 열 때 자동으로 수행된다. 기존 행은 `'unknown'`이 된다 — 그것이 사실이기 때문이다.
- `tax_exempt_assets`는 조립부가 어떤 종목이 ETF인지 알아야 한다. 엔진이 대신 판정해 줄 방법은 종목 마스터를 들여오는 것뿐이고, 그것은 이 결정의 범위가 아니다.

**남는 것**

`LiveDataHandler`는 여전히 어떤 ABC도 구현하지 않고(보고서 §9-1), `BacktestTradingSession`은 브로커·거래소를 하드코딩한다(§9-2). 후자가 풀리기 전에는 "실시간 시세에 대고 로컬 가상 체결" 형태의 페이퍼 트레이딩을 조립할 수 없다.

**검증**

- 원장 신원 10건: 스탬프·재스탬프·모드/venue/계좌 3종 충돌·메시지 내용·행 단위 mode·`'unknown'` 기본값·구버전 마이그레이션.
- 승격 기준 4건: 신원 없는 원장 거부, 실전 원장 거부, 혼입 행 검출, 통과 시 배포 명시.
- ETF 면제 2건: 면제 자산은 수수료만·개별주는 세금까지, 그리고 기본값이 면제 없음.
- 732 케이스 통과, `ruff check` 통과.
