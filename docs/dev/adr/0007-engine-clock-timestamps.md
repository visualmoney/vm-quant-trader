# ADR-0007: 엔진 회계의 타임스탬프는 단조 증가하는 엔진 시계를 쓴다

| 항목 | 내용 |
| --- | --- |
| 상태 | **채택됨 (Accepted)** — 구현됨 (2026-08-20, Phase 2) |
| 작성일 | 2026-08-19 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §10.2 |
| 관련 요구 | FR-22, C-13 ([spec/kis-broker.md](../spec/kis-broker.md)), 실패모드 F15 |

## 맥락

라이브에서 체결은 시간에 걸쳐 도착한다([ADR-0006](0006-decouple-submit-from-fill.md)). 그러면 `Transaction`에 어느 시각을 넣을 것인가 — 브로커가 알려준 **체결 시각**인가, 엔진이 그것을 확인한 **엔진 시각**인가.

직관적으로는 체결 시각이 정확해 보인다. 그러나 `Portfolio`가 타임스탬프의 **단조성을 강제**한다.

```
broker/portfolio/portfolio.py:208-214    if txn.dt < self.current_dt: raise ValueError(...)
broker/portfolio/portfolio.py:311-317    if current_dt < self.current_dt: raise ValueError(...)
broker/portfolio/position.py:119-125     동형
```

그리고 정산 단계의 폴링은 **미결 주문 집합을 순회**하므로, 체결 순서와 확인 순서가 일치한다는 보장이 없다.

## 결정

**`Transaction.dt`와 시가평가 시각은 엔진 시계에서 얻는다.** 엔진 시계는 단조 증가하며, 브로커가 알려준 체결 시각은 **원장에만** 기록한다(감사·분석용).

## 검토한 대안

| 대안 | 내용 |
| --- | --- |
| 대안 1 | 브로커 체결 시각을 그대로 `Transaction.dt`에 쓴다 |
| 대안 2 | 체결 시각을 쓰되, 역전이 발생하면 `max(체결시각, current_dt)`로 클램프한다 |

## 근거

**대안 1은 세션을 죽인다.** 구체적 시나리오:

1. 주문 A가 09:31에 체결되고, 주문 B가 09:33에 체결된다.
2. 정산 폴링이 B를 먼저 확인해 반영한다 → `Portfolio.current_dt = 09:33`.
3. 이어 A를 반영한다 → `txn.dt = 09:31 < 09:33` → **`ValueError`** (`portfolio.py:208-214`).

시가평가가 사이에 끼면 더 쉽게 터진다. `update(dt)`가 `dt`로 평가한 뒤 그보다 앞선 체결시각의 `Transaction`이 들어오면 같은 예외다.

**대안 2는 예외는 막지만 의미를 망친다.** 클램프된 시각은 체결 시각도 아니고 확인 시각도 아닌 값이 되어, 이후 어떤 분석도 신뢰할 수 없다. 예외를 숨기는 대신 데이터를 오염시킨다.

**엔진 시계는 백테스트와도 정합적이다.** 백테스트에서 `Transaction.dt`는 시뮬레이션 엔진이 부여한 시각이지 거래소가 알려준 시각이 아니다(`broker/simulated_broker.py:599-602`의 `self.current_dt`). 라이브에서 엔진 시계를 쓰는 것은 **같은 규칙의 연장**이다.

같은 결론을 `smtm`도 인터페이스에 명시했다 — `Trader` ABC의 콜백 계약이 `date_time`을 *"거래 체결 시간, 시뮬레이션 모드에서는 request의 시간"*으로 분기한다(`smtm/trader/trader.py:41`). 시각의 출처가 실행 평면에 따라 다르다는 것을 계약 수준에서 인정한 것이다.

## 결과

- **체결 시각의 정밀도를 회계에서 잃는다.** 09:31 체결을 09:34에 확인했다면 회계상 09:34다. 일~주 단위 리밸런싱(스펙 §2)에서 이 오차는 무의미하다.
- **원장은 두 시각을 모두 보관한다** — 브로커 체결시각과 엔진 반영시각. 감사·슬리피지 분석은 원장을 쓴다 (NFR-5).
- 엔진 시계는 **주입 가능**해야 한다. 테스트가 가짜 시계로 순서 역전을 재현할 수 있어야 한다 (F15 대응 테스트).
- 시계는 **단조성을 스스로 보장**해야 한다. 시스템 시각이 NTP 보정으로 뒤로 갈 수 있으므로, 마지막 발행 시각보다 앞서지 않도록 클램프한다.
