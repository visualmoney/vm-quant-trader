# ADR-0010: 대화형 운용은 분리 평면의 경량 텔레그램 게이트웨이 데몬이 제공한다

| 항목 | 내용 |
| --- | --- |
| 상태 | **제안됨 (Proposed)** — 미구현. [ADR-0009](0009-cron-oneshot-live-session.md)를 **보강**한다 (대체 아님 — 트레이딩 평면은 무변경) |
| 작성일 | 2026-08-20 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §10.4, §11 Q11 |
| 관련 요구 | FR-19·FR-25, NFR-9·NFR-10, C-15 ([spec/kis-broker.md](../spec/kis-broker.md)) |

## 맥락

운용자는 텔레그램으로 (a) 계좌 현황 조회, (b) 주문 현황 조회, (c) 거래 중지(킬스위치)를 **대화로** 요청하는 운용을 원한다. 호스트에는 kakao 알림 토큰 cron이 이미 있으나 단방향 알림일 뿐, 양방향 대화 평면은 없다. 물음은 **"이 요구가 ADR-0009(cron 단발)를 폐기시키는가"**였다.

대조군 `smtm`의 텔레그램 컨트롤러를 정독했다 (2026-08-19, 전부 직접 검증):

- **수신 구조는 가볍다** — 텔레그램 SDK 없이 `requests`+표준 라이브러리만 import하고(`controller/telegram/message_handler.py:9-16`), daemon 스레드가 `getUpdates` long-polling(`timeout=10`, `:30`·`:146-149`)을 0.5초 루프로 돈다(`:89-104`). 인증은 단일 `chat_id` 필터(`:130-131`), 송신은 `smtm/worker.py` 큐로 비동기(`:76-77`, `:166-172`).
- **명령 배선은 무겁고 위험하다** — 명령 콜백(`operator.chat`)이 **폴링 스레드에서 실행**되고(`telegram_controller.py:38, 85-96` ← `message_handler.py:132-133`) 메인 스레드는 sleep만 한다(`telegram_controller.py:82-83`). 트레이딩은 컴포넌트별 워커 스레드에서 돈다 — 우리 NFR-8("`Portfolio`·엔진 시계는 메인 스레드 전용")과 양립하지 않는 배선이다.

자원 근거 (전부 **추정** — t3.micro 실측 아님): 검토 환경 실측으로 `python + requests + sqlite3` import 직후 maxrss 약 **26MiB**, 프로젝트 venv `pandas` import 직후 약 **66MiB**. 엔진 가동 피크는 NFR-9가 400MiB로 상한. 호스트 가용 메모리는 260~590MiB 변동(C-15), 동거 실계좌 봇의 주문 집행 슬롯은 14:30~15:20 KST.

## 결정

**트레이딩 평면(ADR-0009 cron 단발)은 무변경으로 유지하고, 대화형 운용은 별도 상주 프로세스 — 경량 텔레그램 게이트웨이 데몬(`scripts/telegram_gateway.py`)이 제공한다.**

| # | 규칙 |
| --- | --- |
| 1 | **무의존 경량**: 게이트웨이는 pandas·vmtrader·OTA를 import하지 않는다(`requests`+`sqlite3`만). 상주 RSS 상한 **80MiB** (NFR-10 — import 실측 26MiB의 3배 여유, **추정**이며 Phase 3에서 실측) |
| 2 | **결합은 파일·DB뿐**: 원장 SQLite **읽기 전용**(URI `mode=ro`) + 킬스위치 **플래그 파일** 쓰기·삭제. IPC·소켓·공유 메모리 금지. 엔진 프로세스·`Portfolio`에 닿지 않으므로 NFR-8 스레드 경계가 적용될 일이 없다 |
| 3 | **FR-19 킬스위치의 매체는 플래그 파일로 확정**: 게이트웨이(또는 운용자)가 쓰고, 엔진 가드(`broker/kis/guards.py`)가 기동 초입·매 접수·매 폴링 반복에서 읽는다. 해제도 대칭(파일 삭제) |
| 4 | **smtm 이식 범위**: `message_handler.py`의 수신 구조(long-polling·`chat_id` 필터·송신 워커)는 이식한다. 명령이 폴링 스레드에서 오퍼레이터 상태를 직접 만지는 배선(`telegram_controller.py:85-96`)은 **이식하지 않는다** — 게이트웨이의 명령 처리는 원장 읽기·플래그 쓰기·(선택) KIS 조회뿐이다 |
| 5 | **게이트웨이는 24시간 상주를 권고** (systemd `Restart=always`): 엔진과 달리 30~50MiB급(추정) 읽기 전용 프로세스는 개장 시간 한정의 자원상 이유가 없고, 한정하면 장외에 텔레그램이 침묵해 "저녁에 오늘 체결을 묻는" 용례가 죽는다 |

계좌 현황의 1차 구현은 원장·자본곡선 스냅샷("마지막 기동 기준"임을 응답에 명시)이다. KIS 잔고 직조회(2차)는 엔진∥게이트웨이의 토큰 캐시 공유 잠금이 미확인이라(스펙 §8) 해소 전에는 하지 않는다.

## 검토한 대안

| 대안 | 내용 | 기각 사유 |
| --- | --- | --- |
| 1. 개장 시간 한정 상주 엔진 (smtm 형식) | cron이 09:00경 엔진+텔레그램 한 프로세스를 띄우고 15:30 후 자체 종료 | t3.micro에서 **가능하나 권고 불가**: (a) 유휴 엔진 100~250MiB 추정(pandas import만 66MiB 실측)이 가용 최저 260MiB 호스트에 6.5시간 상주 — 동거 실계좌 봇의 집행 슬롯(14:30~15:20)과 정면 겹쳐 스왑 진입 시 NFR-7(10분 예산)이 깨진다, (b) ADR-0009 폐기 + ADR-0008 개정(사이클 수명·명령→메인 스레드 배선 재설계)이 필요 — smtm 배선은 명령이 폴링 스레드에서 상태를 만져 NFR-8과 양립 불가, (c) FR-7 "매 기동=재기동" 이점(복구 코드가 매일 도는 정상 경로) 소멸 |
| 2. 24시간 상주 엔진 (systemd) | 완전 상주 + 텔레그램 | 대안 1의 모든 문제 + 노출 시간이 24시간으로 확대, C-2 토큰 24h 만료의 장중 갱신 경로 신설, 야간 크래시의 무감시 시간 |
| 3. 대화도 cron 단발 (주기 폴링 잡) | 게이트웨이를 분 단위 cron으로 | 응답 지연이 cron 주기(분 단위)로 늘어 "대화"가 아니게 된다. `getUpdates` long-poll의 즉시성(수초 응답)이 상주의 존재 이유 |

## 근거

1. **자원 비대칭**: 게이트웨이 30~50MiB(추정 — import 실측 26MiB 기반) vs 상주 엔진 100~250MiB(추정). 전자는 가용 최저 260MiB에서도 무해하고, 후자는 실계좌 동거 봇을 위협한다. "가능"과 "권고"를 가르는 것은 이 수치다.
2. **ADR 무손상**: 결합을 원장 읽기·플래그 파일로 한정하면 ADR-0008(스레드 경계)·ADR-0009(단발 수명) 모두 무변경이다 — 대화형 요구는 별도 평면 추가로 전량 흡수된다.
3. **지연이 충분하다**: 조회 응답은 long-poll 수신 즉시 1~3초. 킬스위치는 플래그 쓰기 <1초 후, 사이클 실행 중이면 가드가 매 접수·매 폴링 반복에서 확인해 **수초** 내 접수 중단(설계 §10.5-⑤), 사이클 밖이면 주문 자체가 구조적으로 0건이고 다음 기동 초입에서 차단 — 즉 "주문이 나갈 수 있는 모든 시점"에서 유효하다.
4. **관례와의 관계**: 호스트 최초의 상주 프로세스가 생기지만, 주문을 내지 않는 읽기 전용 경량 데몬이다 — 기존 kakao 단방향 알림 cron을 양방향으로 확장하는 위치이며, 트레이딩 평면의 cron+flock 관례는 그대로다.

## 결과

- 신규 모듈 `scripts/telegram_gateway.py` — vmtrader 패키지 밖(설계 §3.2). NFR-10의 무의존은 `grep` import 경계 테스트로 강제한다.
- FR-19 킬스위치의 매체가 플래그 파일로 확정된다 — `guards.py`의 계약에 반영.
- 계좌 현황은 실시간 인메모리가 아니라 원장 스냅샷이다 — cron 단발 모델에서는 장중 대부분 인메모리 상태 자체가 없으므로 이는 모델의 귀결이다.
- 게이트웨이 크래시는 대화 불능일 뿐 트레이딩에 무영향 — systemd가 재기동한다. 엔진 크래시 의미론(FR-7)도 무변경.
- 미국장(해외주식) 확장 시에도 게이트웨이는 무변경이다 — 시장을 모르고 원장·플래그만 다룬다. 엔진 상주로의 전환 압력이 생기지 않는다.
- **과도기 조건부**: 대안 1 기각 사유 (a)의 집행 슬롯 경합은 **과도기 제약**이다 — hybridma 실집행이 본 엔진으로 교체되면(스펙 §1) 소멸한다. 교체 후에도 (b) ADR-0008/0009 재설계 비용과 (c) FR-7 이점 소멸이 유효하므로 기각은 유지하되, 그 시점에 상주 엔진(미국장 확장 포함)의 재검토 여지는 남는다.
- systemd 유닛·`chat_id` 등록·플래그 파일 경로는 Phase 3 운용 가이드(`docs/user/`)에 기록한다.
