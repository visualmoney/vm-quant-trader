# ADR-0012: 신호용 과거 시세는 브로커에서 받고, 매 기동마다 버퍼를 채운다

| 항목 | 내용 |
| --- | --- |
| 상태 | **채택됨 (Accepted)** — 구현됨 (2026-08-20) |
| 작성일 | 2026-08-20 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §11 Q3 |
| 관련 요구 | FR-10, NFR-1·NFR-4, [ADR-0009](0009-cron-oneshot-live-session.md) |

## 맥락

`SMASignal`·`MomentumSignal` 등은 과거 종가를 요구한다. 라이브 설계는 사이징용 마크(현재가)만 다뤘고 신호용 시계열의 조달처가 비어 있었다(Q3).

**코드를 읽어 보니 물음이 하나가 아니라 둘이었다.**

신호 버퍼는 `deque(maxlen=lookback)`이고(`signals/buffer.py:115-124`), `SignalsCollection.update(dt)`가 **하루에 한 가격씩** 채운다(`signals/signals_collection.py:57-60`). 백테스트는 시작일부터 끝까지 달리므로 버퍼가 저절로 찬다. 그러나 [ADR-0009](0009-cron-oneshot-live-session.md)가 라이브를 **cron 단발**로 정했으므로 **매 기동이 빈 버퍼에서 시작한다.** 워밍업이 없으면 200일 이동평균이 매일 **당일 가격 하나로** 계산된다 — 조달처를 정해도 이 문제는 남는다.

KIS API를 실측했다(2026-08-20, MCP):

| 사실 | 값 |
| --- | --- |
| 일봉 API | `inquire_daily_itemchartprice` (TR `FHKST03010100`) |
| 모의계좌 | **동작함** — TR이 실전과 동일 |
| 1회 최대 | **100건** — 200일 룩백은 2회 이상 |
| 수정주가 | `fid_org_adj_prc` = `0`(수정) / `1`(원주가) |
| 응답 필드 | output2의 `stck_bsop_date`(영업일자)·`stck_clpr`(종가) |

## 결정

**조달처는 브로커(KIS 일봉 API)이고, 라이브 세션은 매 기동마다 신호 버퍼를 워밍업한다.**

| 항목 | 규칙 |
| --- | --- |
| 조달처 | `BrokerClient.get_daily_closes(symbol, start, end, adjusted)` — Protocol의 일부이므로 엔진은 SDK를 모른다 |
| 계약 | `LiveDataHandler.get_assets_historical_range_close_price(...)` — **`BacktestDataHandler`와 같은 이름·같은 모양**이다. 워밍업 코드가 양 평면에서 동일하게 돈다 |
| 수정주가 | **기본 적용**(`adjusted=True`). 미조정 액면분할은 이동평균에 **50% 폭락**으로 읽힌다 |
| 워밍업 시점 | 리밸런싱 기동의 사이징 **직전**. 장 마감 기동은 하지 않는다(거래하지 않으므로) |
| 요청 폭 | 룩백 × 1.75 + 10 **역일**. 주말·휴장일 때문에 룩백만큼 요청하면 30% 부족하다 |
| 요청 횟수 | 컬렉션 내 **최장 룩백 1회**로 전 종목·전 신호를 채운다. 비싼 것은 데이터가 아니라 레이트리밋이다 |
| 이력 결손 | 종목별 워밍 건수를 반환하고, **0인 종목이 있으면 그날은 거래하지 않는다** |

## 검토한 대안

| 대안 | 내용 | 기각 사유 |
| --- | --- | --- |
| 1. 기존 CSV 재사용 | 백테스트가 쓰는 CSV를 라이브도 읽는다 | 별도 일일 다운로드 잡이 필요하고, 그 잡이 실패하면 **조용히 낡은 가격으로 신호를 계산**한다. 거래 상대와 데이터 출처가 갈리는 것도 나쁘다 |
| 2. 버퍼를 프로세스 밖에 영속화 | 원장에 버퍼를 저장해 다음 기동이 이어받는다 | 상태가 하나 더 늘고, 그 상태가 틀렸는지 **확인할 방법이 없다**. 브로커에서 다시 받으면 매번 검증된 값이다. ADR-0009가 "기동 간 상태는 원장과 브로커 잔고뿐"으로 정한 것과도 어긋난다 |
| 3. 워밍업 없이 며칠 굴려 채우기 | 기동을 반복하면 언젠가 찬다 | 200일 룩백이면 **200거래일(약 10개월)** 뒤에야 신호가 유효해진다. 그동안 잘못된 신호로 거래한다 |
| 4. 신호 계층을 라이브 비범위로 | 고정 비중 전략만 운용 | 알파모델을 양 평면에서 재사용한다는 이 연동의 목적(§1.1)을 절반 포기하는 것이다 |

## 근거

**같은 계약으로 두는 것이 핵심이다.** 워밍업 함수는 `get_assets_historical_range_close_price`만 알고, 그 메서드는 백테스트 핸들러에도 있다. 라이브가 다른 출처에서 프라이밍하면 **같은 전략이 두 평면에서 다른 신호를 낸다** — 백테스트 성과가 라이브를 예측하지 못하게 되는, 스펙 §1.1이 피하려던 바로 그 상황이다. 테스트가 이를 못 박는다: 워밍업한 신호값이 같은 가격을 손으로 먹인 값과 일치해야 한다.

**이력이 없으면 거래하지 않는다.** 신호는 이력이 없어도 **숫자를 반환한다** — 버퍼에 하나뿐인 가격의 평균은 그 가격 자신이다. 조용히 틀린 값으로 사이징하는 것보다 하루 쉬는 편이 낫다.

## 결과

- `BrokerClient` Protocol에 메서드가 하나 늘었다. 게이트웨이는 100건 제한을 **역방향 페이징**으로 넘고, 짧은 페이지를 만나면 멈춘다(더 옛날 데이터가 없다는 뜻).
- **레이트리밋 비용**: 종목 20개 × 룩백 200일이면 종목당 3회 = 60회 호출. 모의계좌 스로틀 0.5초 기준 약 30초로, 시간 예산(FR-23) 안이지만 무시할 수 없다. 룩백이 길수록 비싸진다.
- 백테스트 경로는 **무변경**(NFR-4). 워밍업은 라이브 세션만 호출한다.
- 남은 미확인: 수정주가 계산이 백테스트 CSV의 조정 방식과 일치하는지는 **미검증**이다. 두 평면의 신호를 실제로 대조해 봐야 알 수 있다 — Phase 3 스모크 항목에 추가한다.
