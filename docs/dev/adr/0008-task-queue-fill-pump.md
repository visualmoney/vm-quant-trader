# ADR-0008: 체결 수집의 실행 기반으로 단일 FIFO 태스크 큐 워커를 채택한다

| --- | --- |
| 상태 | **제안됨 (Proposed)** — 미구현. [ADR-0006](0006-decouple-submit-from-fill.md)을 **보강**한다 (대체 아님) |
| 작성일 | 2026-08-19 |
| 맥락 | [spec/kis-broker-design.md](../spec/kis-broker-design.md) §10.3, §10.6 |

## 맥락

ADR-0006은 주문 접수와 체결 반영을 분리했다. 남은 물음은 **정산(settle) 단계를 어느 실행 기반 위에서 돌리는가**다. 원안은 메인 스레드가 미결 집합을 순회 폴링하는 것이었다. 이 방식의 약점 둘:

1. **접수와 수집이 겹치지 않는다** — 접수 전건이 끝나야 첫 폴링이 시작된다.
2. **메인 스레드가 폴링 `sleep`에 갇힌다** — 킬스위치(FR-19)·종료 신호 확인이 폴링 간격 단위로만 가능하다.

한편 사용자 지시는 `smtm/worker.py`의 응용이었다. 정독 결과 worker.py는 §10.3에서 기각된 "콜백 계약"이 아니라, **스레드 1개가 `queue.Queue`를 FIFO로 소화하는 직렬화 프리미티브**다 — 적재(`worker.py:36-43`), 순차 소화(`:57-80`, `get`은 `:62`), `None` 센티넬 종료(`:64-70`), 예외 시 강제 정지(`:75-80`), `stop()`은 센티넬 투입 후 join(`:85-95`).

결정적으로, 참조 구현 `vm-quant-lab`(KIS 실계좌 가동 중)이 **정확히 이 조합을 이미 구현했다**: smtm worker.py를 이식한 `FillPumpWorker`(`adapters/live/worker.py:1`, 의도적 차이 3건 `:10-14`)와, 접수 즉시·폴링 워커 위임·drain의 `PumpedKisExecution`(`adapters/live/pumped.py:7-8`), 그리고 `execution.mode="pumped"` 명시 선택 배선(`run.py:690-699`, 기본은 sync `:672-675`).

## 결정

**정산 단계의 체결 폴링을 단일 FIFO 태스크 큐 워커 스레드에서 실행한다.** 모듈은 `vmtrader/broker/kis/worker.py`(lab `FillPumpWorker` 이식 — ADR-0003과 정합).

| 항목 | 규칙 |
| --- | --- |
| 수명주기 | `KisBroker`가 리밸런싱 사이클마다 생성. 첫 `submit_order`에서 기동, `settle(deadline)` 말미에 `stop()`(센티넬+join). daemon=False, **상주 금지** |
| 태스크 | **폴링 태스크 한 종류**(`order_no`·`order_key`·`requested`·`deadline`) + 종료 센티넬 `None`. 부수 작업의 비동기화는 하지 않는다 |
| 태스크 동작 | 종결·데드라인·킬스위치까지 폴링 → 체결 증분을 (a) 스레드별 SQLite 연결로 원장 기록, (b) 락 버퍼에 적재 |
| **스레드 경계 (핵심)** | `Portfolio`·`Position`·엔진 시계·`Transaction` 생성은 **메인 스레드 전용**. 워커↔메인 공유 상태는 락 버퍼와 원장뿐 (NFR-8) |
| 정산 | 메인 스레드는 감시 루프(킬스위치·데드라인)를 돌다 join → 버퍼를 FIFO로 드레인해 `transact_asset`(엔진 시계, ADR-0007) |
| 종료 시퀀스 | 접수 중단 → 잔여 태스크 조기 소진 → `stop()`(적재분 전부 소화 후 종료 — 유실 0) → 버퍼 드레인 → 미결 STALE. 취소 주문 없음 |
| STALE 흡수 | `update(dt)`는 워커 없이 메인 스레드 1회 조회 |

백테스트 경로에는 스레드가 도입되지 않는다. 워커는 `KisBroker` 내부 구현이며 `Broker` ABC에 나타나지 않는다 (NFR-4).

## 검토한 대안

| 대안 | 내용 | 기각 사유 |
| --- | --- | --- |
| 1. 메인 스레드 순차 정산 (C 원안) | `settle(deadline)`이 미결 집합을 직접 순회 폴링 | 동작은 하나 접수·수집이 안 겹치고, 폴링 `sleep` 동안 반응성이 없다. 워커안의 **폴백 경로로는 유지**한다(lab의 sync 모드처럼 기본 안전 경로) |
| 2. B 전면 채택 (상주 워커 + 콜백 계약) | smtm처럼 `Broker` 밖 제어 흐름 | ADR-0006에서 기각, 유지 — 백테스트/라이브 코드경로가 갈라진다 |
| 3. asyncio | 이벤트 루프로 폴링 동시화 | 엔진 전체가 동기 코드다. 색깔 전염(async 함수 전파)이 코어를 침습하고, OTA도 동기다 |
| 4. 주문별 스레드 N개 | 폴링 병렬화 | 레이트리밋(NFR-1)과 정면 충돌. lab도 단일 FIFO·PriorityQueue 금지를 명시(`worker.py:16-17`) |

## 근거

**경합 배제의 실증 선례.** `Portfolio`는 스레드 안전하지 않고 단조성 가드가 순서에 민감하다(`portfolio.py:208-214`, `:311-317`, `position.py:119-125`). lab은 같은 문제를 "워커는 회계를 만지지 않는다"로 풀었다 — 체결 증분은 락 버퍼에만 적재하고(`pumped.py:109-114`, `:247-251`), 가드 통지조차 메인 스레드가 join 후 일괄 적용하며(`:170-175`), SQLite는 스레드별 연결이다(`:91-93`). smtm의 교훈("상태 변경을 큐 하나로 직렬화")을 회계에는 "메인 스레드 단일 작성자"로 번역한 것이다. smtm 자체는 오퍼레이터·트레이더가 각자 워커를 가져 콜백이 스레드 경계를 넘으므로(`trading_operator.py:101-105`의 `strategy.update_result`가 트레이더 워커에서 실행) 그대로 이식하지 않는다.

**멱등성과의 결합.** 비동기 수집은 같은 주문의 누적 스냅샷을 여러 번 본다. lab의 증분 환산(`pumped.py:41-62`)과 멱등키 `주문번호:누적체결수량`(`:65-77` — `inquire_daily_ccld`에 체결번호가 없다는 실측 근거 포함)이 NFR-6과 정확히 맞물린다.

**단일 작성자와 ADR-0007의 정합.** 엔진 시계 발행과 `transact_asset`이 메인 스레드 한 곳이므로 단조 클램프가 단순해진다. 워커가 회계에 쓰면 이 보장이 무너진다.

## 결과

- **스레드 1개가 라이브 경로에 들어온다.** 비용: 락 버퍼, 스레드별 원장 연결 팩토리, 그리고 **게이트웨이 스레드 안전성**(메인 `place_order` ∥ 워커 체결조회 — lab `ratelimit.py`에는 락이 없어 본 저장소가 추가한다, NFR-8).
- **head-of-line 지연**: FIFO라 앞 태스크의 폴링이 뒤 태스크 확인을 늦춘다. 공유 데드라인(FR-23)이 최악을 절단한다.
- **테스트는 순서 테스트다**: 스레드가 1개라 FIFO 순서·센티넬 종료·drain 배리어를 검증하면 된다. 정산 테스트는 가짜 클라이언트+주입 `sleep`으로 "워커 경로에 `transact_asset` 부재"를 단언한다 (설계안 §8).
- 구현 순서는 lab을 따른다 — **메인 스레드 정산(대안 1)을 먼저 만들고, 워커 기반을 같은 계약의 두 번째 구현으로 얹는다.** 검증 안 된 동시성을 기본값으로 두지 않는다(`run.py:672-675`의 규율).
