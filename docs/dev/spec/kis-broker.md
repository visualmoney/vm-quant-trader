## 1. 목적과 배경

QSTrader의 `Broker` ABC는 처음부터 라이브를 전제로 쓰였다. 클래스 docstring이 그렇게 선언한다 — *"Both simulated and live brokers will be derived from this ABC. This ensures that trading algorithm specific logic is completely identical for both simulated and live environments."* (`qstrader/broker/broker.py:6-10`)

그러나 상속 구현체는 `SimulatedBroker` 하나뿐이고, `TradingSession` 구현체도 `BacktestTradingSession` 하나뿐이다(`qstrader/trading/` 디렉터리에 `backtest.py`와 ABC만 존재). 즉 **설계 의도만 있고 라이브 평면은 비어 있다.** 이 스펙은 그 빈 평면을 KIS 국내주식 현물로 채우기 위한 요구사항을 정의한다.

부가 배경: 같은 사용자의 별도 저장소 `vm-quant-lab`이 이미 KIS 연동을 가동 중이다(`packages/adapters/live/`, `packages/brokers/kis/`). 검증된 파서·클라이언트·원장·가드가 존재하므로, 본 연동은 **백지 개발이 아니라 검증된 자산의 재사용 문제**다.

### 1.1 왜 백테스트 엔진에 붙이는가

| 대안 | 문제 |
| --- | --- |
| lab에서만 라이브 운용 | 백테스트(qstrader)와 라이브(lab)의 사이징·회계 코드가 다르다 → 백테스트 성과가 라이브를 예측하지 못한다 |
| 신규 라이브 엔진 작성 | 알파모델·리밸런싱·통계 계층을 두 번 만든다 |
| **qstrader에 라이브 브로커 추가 (본안)** | 알파모델·`PortfolioConstructionModel`·`OrderSizer`·통계가 **그대로** 라이브에 재사용된다 |

## 3. 용어

| 용어 | 정의 |
| --- | --- |
| OTA | `open-trading-api` — KIS 공식 파이썬 예제 저장소. lab은 이를 `sys.path`에 주입해 래핑한다 |

## 4. 기능 요구사항

| ID | 요구사항 | 검증 방법 |
| --- | --- | --- |
| **FR-1** | `KisBroker`는 `Broker` ABC의 추상 메서드 **12개 전부**(`broker.py`의 `@abstractmethod` 12건)와 `update(dt)`를 구현한다 | 인스턴스화 성공 + `tests/unit/test_abstract_base_classes.py` 방식의 미구현 검출 테스트 |
| **FR-2** | 양수 수량 `Order`는 매수, 음수 수량은 매도로 KIS 시장가 주문(`order_cash`)을 접수하고 주문번호(`ODNO`)를 획득한다 | 가짜 `BrokerClient` 주입 후 호출 인자·부호 매핑 단위 테스트 |
| **FR-3** | 접수한 주문의 체결 현황을 주문번호로 폴링(`inquire_daily_ccld`)해 **누적체결수량·평균단가·수수료**를 얻고, 그 값으로만 `Transaction`을 만든다. 미체결·부분체결도 정확히 반영한다 | 폴링 3회 후 부분체결로 종료되는 가짜 클라이언트 시나리오 테스트 |
| **FR-4** | 주문 체결량이 0이면 `Transaction`을 생성하지 않는다 (포트폴리오 무변화) | 체결 0 시나리오 테스트 — 포트폴리오 해시 불변 |
| **FR-5** | `get_portfolio_as_dict()`는 기존 계약(자산 심볼 키, `quantity`/`market_value`/`unrealised_pnl`/`realised_pnl`/`total_pnl` 하위 dict)을 그대로 만족한다 — `OrderSizer`가 `.get(asset, {}).get('quantity', 0)`로 소비하기 때문(`long_short.py:200`, `dollar_weighted.py` 동형) | 사이저를 `KisBroker`에 물린 통합 테스트 |
| **FR-6** | `get_account_total_equity()`는 `"master"` 키를 포함한다 — `BacktestTradingSession._update_equity_curve`가 `["master"]`로 직접 접근한다(`backtest.py:342`) | 반환 dict 키 단언 |
| **FR-7** | 프로세스 기동 시 KIS 잔고(`inquire_balance`)를 조회해 로컬 `Portfolio`를 재구성한다. 재구성 결과의 종목·수량은 브로커 응답과 일치해야 한다 | 잔고 응답 fixture → `Portfolio` 상태 단언 |
| **FR-8** | 실행 중 브로커 잔고와 로컬 포지션이 불일치하면 **감지해 로그·보고**한다. 로컬이 실제보다 많이 보유했다고 믿는 경우(과대 계상)는 **매매를 중단**한다 | 불일치 fixture로 중단 여부 단언 |
| **FR-9** | KRX 장운영시간·휴장일을 판정하는 `Exchange` 구현체를 제공한다. 장외 시각에는 주문을 접수하지 않는다 | 개장/폐장/주말/휴장일 경계 시각 파라미터화 테스트 |
| **FR-10** | 사이징·평가에 쓰는 시세를 KIS에서 공급하는 `DataHandler`를 제공한다. 기존 `get_asset_latest_ask_price` / `get_asset_latest_bid_ask_price` / `get_asset_latest_mid_price` 시그니처를 유지한다 | 사이저·브로커가 수정 없이 동작하는 통합 테스트 |
| **FR-11** | 주문 수량은 **정수 주**다. 소수 수량은 절대값 기준 내림하고, 내림 결과 0주면 무주문 | 0.9주·1.4주·-1.4주 입력 테스트 |
| **FR-12** | 계좌 기준통화는 **KRW**다. `SimulatedBroker._set_base_currency`가 참조하는 `settings.SUPPORTED['CURRENCIES']`(현재 `USD`/`GBP`/`EUR`, `settings.py:1-4`)에 KRW가 추가되어야 한다 | `base_currency="KRW"` 인스턴스화 성공 |
| **FR-13** | 증권거래세는 **매도 시에만** 부과하는 `FeeModel`을 제공한다. 현행 `PercentFeeModel`은 매수·매도 구분 없이 tax를 부과한다(`percent_fee_model.py:47-68`) | 동일 수량 매수/매도 각 1건의 `calc_total_cost` 비대칭 단언 |
| **FR-14** | 목표 수량이 음수(공매도)인 주문은 **거부**한다. 매도 수량은 현재 보유 수량을 초과할 수 없다 | 보유 10주 상태에서 -15주 주문 거부 테스트 |
| **FR-15** | 기본 서버는 `vps`(모의투자)다. `prod`(실전)는 **호출부에서 명시 지정**해야만 선택된다. 기본값 폴백으로 실전에 연결되는 경로가 없어야 한다 | 인자 미지정 시 `vps` 단언 + `prod` 지정 경로의 명시성 검토 |
| **FR-16** | 모든 주문의 **의도·접수·체결·거부**를 영속 저장소에 append-only로 기록한다. 기록은 프로세스 종료 후에도 남는다 | 원장 파일 기동 간 지속 테스트 |
| **FR-17** | 라이브 리밸런싱 스케줄을 실행하는 `TradingSession` 구현체를 제공한다. 백테스트와 **동일한** `QuantTradingSystem`·알파모델·사이저를 사용한다 | 가짜 브로커·가짜 시계로 하루치 세션 실행 통합 테스트 |
| **FR-18** | 계좌 입출금(`subscribe_funds_to_account` / `withdraw_funds_from_account` / `*_from_portfolio`)은 **미지원**으로 명시적 예외를 던진다. KIS API는 자금 이체를 제공하지 않으며, 조용히 로컬 잔고만 바꾸면 브로커와 즉시 불일치한다 | 4개 메서드 호출 시 예외 타입·메시지 단언 |
| **FR-19** | 주문 1건당 최대 금액, 세션당 최대 주문 건수, 외부 킬스위치를 통한 즉시 중단을 지원한다 | 한도 초과 주문 거부 테스트 |

## 5. 비기능 요구사항

| ID | 요구사항 | 검증 방법 |
| --- | --- | --- |
| **NFR-1** | KIS 레이트리밋(`EGW00201` 초당 거래건수 초과)에 대응한다. **조회 계열**은 빈 응답 백오프 재시도, **주문(`order_cash`)은 재시도 금지**(비멱등 — 중복 주문 위험), **체결조회는 재시도 금지**(빈 응답이 정상 미체결과 구분 불가) | 가짜 클라이언트로 재시도 횟수·미재시도 단언 |
| **NFR-2** | 전 테스트가 **네트워크 없이** 통과한다. KIS SDK(OTA)가 설치되지 않은 환경에서도 `import` 및 단위 테스트가 성립한다 | CI에서 OTA 미설치 상태로 전체 스위트 실행 |
| **NFR-3** | KIS SDK·`open-trading-api`·인증 토큰 처리는 **어댑터 1개 모듈에만** 존재한다. `qstrader.broker.kis_broker`를 포함한 엔진 코어는 OTA를 직접 import하지 않는다 | `grep`으로 import 경계 검사하는 테스트 |
| **NFR-4** | 백테스트 코드경로는 **동작이 바뀌지 않는다**. 기존 스위트 전건 통과, 기존 백테스트의 최종 자본이 센트 단위까지 동일 | 기존 e2e fixture(`tests/integration/trading/`) 회귀 |
| **NFR-5** | 주문·체결·거부·불일치는 구조화된 로그로 남는다. 로그만으로 "어느 시각에 무엇을 왜 주문했고 얼마나 체결됐는가"를 재구성할 수 있다 | 로그 필드 목록 리뷰 |
| **NFR-6** | 동일 체결이 포트폴리오에 **두 번 반영되지 않는다** (프로세스 재기동·재조회 시에도) | 같은 체결 스냅샷 2회 반영 시도 → 포지션 불변 단언 |
| **NFR-7** | 종목 20개 리밸런싱 1회가 KIS 레이트리밋 준수 하에 **10분 이내** 완료된다 | 가짜 클라이언트에 실측 지연을 넣은 시뮬레이션 |

## 6. 제약

| ID | 제약 | 영향 |
| --- | --- | --- |
| **C-1** | KIS OTA 클론이 로컬에 있어야 한다 (`OTA_HOME`). PyPI 패키지가 아니다 | 런타임 의존을 선택적(optional)으로 유지해야 한다 |
| **C-2** | KIS 접근토큰은 유효기간이 있고 만료 시 재인증이 필요하다 | 세션 장기 실행 시 재인증 경로 필요 |
| **C-3** | 시장가 주문은 체결가를 사전에 알 수 없다 | 사이징은 현재가 기준 추정, 실제 체결가와 괴리 발생 |
| **C-4** | KRX 개인 계좌는 공매도가 불가하다 | `long_only=True` 강제 (FR-14) |
| **C-5** | 주문 수량은 정수 주다 (`ord_qty`는 문자열 정수) | 사이징 결과 내림 (FR-11) |
| **C-6** | KRX 정규장은 KST 09:00–15:30이며 휴장일은 매년 다르다. **한국 공휴일 캘린더의 조달 방식은 미확인** — KIS API 제공 여부, `exchange_calendars` 패키지 도입 여부는 설계 단계에서 결정한다 | FR-9 구현 방식 미정 |
| **C-7** | 체결 통보는 폴링으로만 얻는다 (웹소켓 비범위) | 폴링 타임아웃이라는 실패 모드가 구조적으로 존재 |
| **C-8** | 국내주식은 D+2 결제다. 예수금(`dnca_tot_amt`)과 실제 주문가능금액은 다르다 | 매수 여력 판정에 여유(buffer)가 필요 |
| **C-9** | 증권거래세는 매도 대금에만 부과된다 | FR-13 |
| **C-10** | `Portfolio`는 인메모리이며 영속화가 없다 (`portfolio.py` 전체 — `history`는 리스트(`:54`), 저장 경로 없음) | FR-7 상태 복구는 브로커 잔고에서 재구성해야 한다 |
| **C-11** | 현행 `SimulatedBroker`는 현금 부족 시 경고만 내고 음수 잔고로 체결한다(`simulated_broker.py:589-596`, `portfolio.py:220-226`). 라이브에서는 주문 자체가 거부된다 | 라이브는 사전 클램프가 필요 |

| **A-2** | **백테스트 무회귀**: 기존 테스트 전건 통과, 60/40 백테스트 최종 자본이 변경 전과 센트 단위까지 동일 | 기존 e2e fixture |
| **A-3** | **모의투자 스모크**: `vps` 계좌에서 2종목 롱온리 리밸런싱 1회를 실제 수행해 (a) 주문번호 획득, (b) 체결 확인, (c) 잔고 조회 결과가 로컬 포트폴리오와 일치 | 수동 스모크 스크립트 + 로그 첨부 |
| **A-4** | **재기동 복구**: A-3 직후 프로세스를 죽이고 재기동했을 때, 잔고 기반 재구성 결과가 A-3 종료 시점 포트폴리오와 일치하고 **동일 체결이 이중 반영되지 않는다** | 수동 스모크 2단계 |
| **A-5** | **안전장치 실증**: (a) 시장 마감 후 주문 시도가 거부되고, (b) 공매도 방향 주문이 거부되고, (c) 킬스위치 작동 시 다음 주문부터 중단된다 | 단위 테스트 3건 + 스모크 1건 |

**실전(`prod`) 계좌 운용은 인수 기준에 포함하지 않는다.** A-1~A-5 통과 후 별도 판단 사안이다.
